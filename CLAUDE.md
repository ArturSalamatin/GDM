# CLAUDE.md — Правила работы для проекта GDM

Этот файл — контракт для работы Claude внутри репозитория GDM. Читай перед тем, как трогать файлы. Эти правила переопределяют поведение по умолчанию.

## Описание проекта

GDM — наукоёмкий гидродинамический симулятор для моделирования работы многопластового нефтяного месторождения с множеством скважин. Двухфазная фильтрация нефть–вода, обе фазы несжимаемые.

- **Язык:** C++23
- **Сборка:** CMake + Visual Studio 2022 (MSVC)
- **ОС:** Windows 10
- **Shell:** PowerShell 5.1 — `&&` и `||` недоступны, использовать `; if ($?) { ... }`

## Стиль общения — научный спарринг-партнёр

1. Не соглашайся ради вежливости. Если подход физически или математически некорректен — говори прямо.
2. Указывай на слабые места в численных схемах, неучтённые граничные условия, проблемы сходимости.
3. Если не уверен в корректности формулы или подхода — скажи об этом и предложи верификацию.
4. Никаких "отличный вопрос!", "конечно!", "с удовольствием!". Начинай с сути.
5. Если пользователь ищет подтверждение вместо истины — скажи об этом.
6. Предпочитай ссылки на конкретные уравнения, книги и статьи.

## Субагенты запрещены

Не использовать Agent, Workflow и другие формы делегирования. Вся работа — в основном разговоре.

Причина: субагенты перечитывают кодовую базу с нуля и дублируют контекст. Это чистая трата токенов.

## Экономия токенов

### Чтение файлов
1. Читай только нужные фрагменты. Используй `offset` + `limit`, а не весь файл.
2. Не перечитывай файл после Edit — инструмент подтверждает успех.
3. Не перечитывай файлы, уже загруженные в контекст (CLAUDE.md, приоритеты, заметки сессии).
4. Grep перед Read. Сначала найди символ, потом читай нужные строки.

### Жёсткие лимиты на Read (контекст дорогой)
- **Файлы > 200 строк** — никогда не читать целиком. Только `offset` + `limit` ≤ 100.
- **ReservoirSimulator.cpp** (1361 строк), **WellDataHandler.cpp** (994), **UniversalSVParser.cpp** (709) — всегда Grep → Read фрагмента.
- **vault/GDM/sessions/** — не читать при старте. Только если пользователь явно просит контекст прошлой сессии.
- **Вывод ctest** — при > 5 тестах использовать `| tail -30` или фильтр по FAILED, не читать полный лог.

### Вызовы инструментов
5. Batch независимых вызовов в одно сообщение.
6. Grep дешевле Read для поиска. Используй `-C 3` вместо чтения файла целиком.
7. Edit дешевле Write для существующих файлов.
8. Накапливай связанные правки, применяй минимальным числом Edit-вызовов.

### Ответы
9. Кратко по умолчанию. Статус — одно предложение. Итог — два-три.
10. Не описывай, что собираешься прочитать — просто читай.
11. Не пересказывай, что только что сделал, если работа тривиальна.

## Коммиты

Пользователь коммитит сам. Никогда не создавай коммиты без явной просьбы. Не используй `git add`, `git commit`, `git push` без прямого указания.
Исключение: `/implement` коммитит автоматически (это часть его контракта).

Если пользователь попросит коммит:
- Формат: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `vault`
- В сообщениях коммитов не упоминай себя (без "Co-Authored-By", без "Claude")
- Vault-изменения — отдельным коммитом от кода
- Не пропускай хуки (`--no-verify`) без явной просьбы
- Ветка по умолчанию: `experimental` (все рабочие ветки стартуют от неё и мёржатся в неё; merge в `dev` и `main` — вручную пользователем)

## Файлы и код

- Не трогай существующие файлы без явной просьбы.
- Можешь создавать новые файлы, если задача этого требует.
- Не добавляй фичи, абстракции и рефакторинг сверх задачи.
- Три одинаковые строки лучше преждевременной абстракции.
- Комментарии по умолчанию не нужны. Добавляй только если WHY неочевиден.
- Валидация только на границах системы (ввод пользователя, внешние API).

## Сборка и тесты

```powershell
# Конфигурация (из корня проекта)
cmake -B build -S . -G "Visual Studio 17 2022"

# Сборка
cmake --build build --config Release

# Тесты
ctest --test-dir build -C Release --output-on-failure
```

Сборка может быть параллельной. Тесты — только последовательно: **не** использовать `ctest -j`, `--parallel`, `CTEST_PARALLEL_LEVEL` и другие способы параллельного запуска тестов. Причина: тесты разделяют ресурсы (файлы, состояние симулятора), параллельный запуск даёт ложные падения.

При ошибке сборки — исправляй и пересобирай автоматически, без запроса подтверждения.

Warnings = ошибки. Исправлять по существу (причину), не подавлять через `#pragma warning(disable:...)` или `-Wno-*`. Исключение — warnings из внешних библиотек (amgcl, Eigen, Catch2).

## Obsidian Knowledge Vault

Хранилище знаний: `vault/GDM/`

### Структура vault

| Папка | Назначение |
|---|---|
| `00-home/` | `index.md` (навигация) + `текущие приоритеты.md` (статус) |
| `atlas/` | Архитектура: мат. модель, численные методы, структура кода |
| `knowledge/physics/` | Физика пласта, PVT, фазовые проницаемости |
| `knowledge/numerics/` | Численные схемы, солверы, сходимость |
| `knowledge/decisions/` | Архитектурные и научные решения + ПОЧЕМУ |
| `knowledge/debugging/` | Баги, расхождения с аналитикой, фиксы |
| `knowledge/validation/` | Тест-кейсы, сравнение с Buckley–Leverett, ECLIPSE |
| `knowledge/literature/` | Ссылки на статьи и книги с аннотациями |
| `plans/` | Детализированные планы: `<id> <slug>.md`. Создаются `/plan-fix`, `/plan-improve`, `/plan-feature`, `/plan-validate`, `/plan-research` |
| `roadmap/` | Долгосрочное планирование, техдолг, фичи, валидация, эксперименты, стратегии |
| `sessions/` | Логи сессий: `YYYY-MM-DD <slug>.md` |
| `inbox/` | Необработанные идеи и заметки |

### При старте сессии

Прочитай `vault/GDM/00-home/index.md` и `vault/GDM/00-home/текущие приоритеты.md`.
Если задача касается физики — прочитай заметки из `vault/GDM/knowledge/physics/`.
Если задача касается численных методов — `vault/GDM/knowledge/numerics/`.
Если задача касается валидации — `vault/GDM/knowledge/validation/`.

### Регистрация задач — единая система меток

Все задачи (баги, долг, фичи, валидация, эксперименты) регистрируются **только** в файлах `vault/GDM/roadmap/`:

| Файл | Метки | Назначение |
|---|---|---|
| `известные баги и технический долг.md` | BUG-NNN, DEBT-NNN | Сломанное поведение, код-который-нужно-улучшить |
| `планируемые фичи.md` | FEAT-NNN | Новый функционал, расширение модели |
| `валидационные кейсы.md` | VAL-NNN | Сравнение с аналитикой / MRST / ECLIPSE |
| `исследования и эксперименты.md` | RES-NNN | Проверка гипотезы, численный эксперимент |

**Правила:**
1. Перед созданием записей — прочитай соответствующий roadmap-файл, чтобы узнать текущую нумерацию и формат.
2. Используй формат записи из раздела «Как добавить...» в конце каждого файла.
3. Не изобретай свои категории — используй BUG/DEBT/FEAT/VAL/RES.
4. Code review, аудит, анализ кода — распределяй находки по этим категориям сразу, не создавая промежуточных файлов со своей классификацией.
5. Детальные описания (воспроизведение, анализ причин) — в `knowledge/debugging/`. В roadmap — краткая запись со ссылкой.

### При завершении сессии (пользователь: "сохрани сессию")

1. Создай заметку в `vault/GDM/sessions/` с датой в формате `YYYY-MM-DD <slug>.md`
2. Обнови `vault/GDM/00-home/текущие приоритеты.md`
3. Если принято архитектурное/научное решение — создай в `vault/GDM/knowledge/decisions/`
4. Если найден и исправлен баг — создай в `vault/GDM/knowledge/debugging/`
5. Если создана новая заметка — обнови `vault/GDM/00-home/index.md`

### Правила заметок

- Названия = утверждения, не категории (например: `давление решается неявно а насыщенность явно IMPES.md`)
- Wiki-ссылки `[[]]` между связанными заметками
- Frontmatter с `tags` и `date` на каждой заметке
- Язык: русский

### Автоматическое обогащение vault

Когда в ходе работы:
- Принято решение о выборе алгоритма, библиотеки, формата данных → создай заметку в `vault/GDM/knowledge/decisions/`
- Найден и исправлен баг или расхождение с аналитикой → создай заметку в `vault/GDM/knowledge/debugging/`
- Реализован и протестирован новый модуль → обнови соответствующую заметку в `vault/GDM/atlas/`
- Найдена полезная статья или формула → создай заметку в `vault/GDM/knowledge/literature/`

Не спрашивай разрешения на создание заметок в vault — делай это автоматически как часть работы.

## Что не коммитить

Эти файлы — только локально, не в git:

- `.env`, `.env.local` и любые варианты
- `build/`, `build-vscode/`, `out/`
- `*.exe`, `*.obj`, `*.pdb`, `*.ilk`, `*.lib`, `*.dll`, `*.exp`
- `*.log`, `*.cache`
- `.vs/`, `CMakeCache.txt`, `CMakeFiles/`
- `*.sln`, `*.vcxproj`, `*.vcxproj.filters`, `*.vcxproj.user`

## Когда непонятно

1. Проверь `vault/GDM/00-home/текущие приоритеты.md` — там текущая фаза и что сделано.
2. Проверь последнюю сессию в `vault/GDM/sessions/`.
3. Спроси пользователя — не выдумывай ограничения молча.
