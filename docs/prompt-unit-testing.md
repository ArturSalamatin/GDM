# Промпт: планирование и реализация юнит-тестов для C++ проекта

## Как использовать

1. Скопируй этот промпт в новый проект.
2. Приложи к нему файл-образец `plan-unit-testing-example.md` (реализованный план из проекта GDM).
3. Отправь промпт Claude вместе с доступом к кодовой базе нового проекта.

---

## Промпт

```
Ты — инженер по тестированию научного C++ кода. Твоя задача — спланировать и реализовать юнит-тесты для библиотеки ядра проекта.

К этому промпту приложен файл `plan-unit-testing-example.md` — это полностью реализованный план юнит-тестирования аналогичного проекта (гидродинамический симулятор, C++23, CMake, Catch2, MSVC). Используй его как образец структуры, конвенций и уровня детализации. Не копируй содержимое — адаптируй подход к текущему проекту.

### ФАЗА 1: АНАЛИЗ (не пиши код, только план)

#### 1.1. Инвентаризация классов

Просканируй кодовую базу и составь список всех классов/структур с нетривиальной логикой:
- Прочитай CMakeLists.txt — найди основную библиотеку (static library) и все .cpp файлы в ней.
- Для каждого .cpp найди соответствующий .h файл.
- Из каждого .h извлеки: имя класса, публичные методы, зависимости (какие другие классы из проекта используются).
- Исключи из списка: тривиальные POD-структуры (только данные, без логики), чисто абстрактные интерфейсы без реализации, сторонние библиотеки.

Результат: таблица вида
| Класс | Заголовок | Модуль | Публичные методы | Зависит от |

#### 1.2. Граф зависимостей и уровни

Построй направленный граф зависимостей между классами проекта:
- Зависимость = класс A использует класс B в своём .h или .cpp (include + использование в методах).
- Игнорируй зависимости от STL и сторонних библиотек.

Назначь каждому классу уровень:
- **Уровень 0**: класс не зависит ни от одного другого класса проекта (только STL / сторонние).
- **Уровень 1**: зависит только от классов уровня 0.
- **Уровень 2**: зависит от классов уровня 0 и/или 1.
- **Уровень N**: зависит от классов уровня ≤ N-1.

Результат: тот же список классов с колонкой "Уровень".

#### 1.3. Группировка по модулям

Определи логические модули проекта (по структуре директорий или по смыслу):
- Например: geometry, physics, math, solver, mesh, io, utils.
- Каждый класс должен принадлежать ровно одному модулю.
- Модули определяют подпапки в tests/unit/ и теги Catch2.

#### 1.4. Определение тестируемых контрактов

Для каждого класса определи, ЧТО тестировать:

**Тестировать:**
- Конструкторы (default, parameterized) — проверить начальное состояние через геттеры.
- Публичные методы — нормальный путь (типичные входы → ожидаемый результат).
- Граничные случаи — нулевые размеры, пустые коллекции, экстремальные значения, деление на ноль.
- Инварианты — свойства, которые должны выполняться всегда (например: сумма насыщенностей = 1, масса > 0, объём > 0).
- Мутации состояния — метод меняет объект, проверить состояние ДО и ПОСЛЕ.
- Round-trip — Save/Load, Accept/Reverse, Serialize/Deserialize.

**НЕ тестировать юнитами:**
- Тривиальные геттеры POD-структур без логики.
- Приватные методы — только через публичный API.
- Интеграцию с внешними солверами, БД, файловой системой — это интеграционные тесты.
- Код, который невозможно вызвать без запуска всего симулятора.

Результат: для каждого класса — список TEST_CASE с кратким описанием (5–10 тестов на класс, больше для сложных классов).

#### 1.5. План файлов и CMake

Составь:
1. Дерево файлов tests/unit/<module>/test_<ClassName>.cpp
2. CMake executable на каждый уровень зависимостей: `<project>_unit_level0`, `<project>_unit_level1`, ...
3. Привязку каждого .cpp к executable соответствующего уровня.

### ФАЗА 3: РЕАЛИЗАЦИЯ

После согласования реализуй тесты поуровнево. Каждый уровень — один цикл:

#### Цикл для уровня N:

1. **CMake**: добавь executable `<project>_unit_levelN` в CMakeLists.txt (если ещё не добавлен).
   - `target_link_libraries(... PRIVATE <core_lib> Catch2::Catch2WithMain)`
   - `catch_discover_tests(... TEST_PREFIX "unit.levelN." PROPERTIES TIMEOUT <30|60>)`

2. **Тесты**: напиши все .cpp файлы для этого уровня. Соблюдай конвенции:

   **Формат имени TEST_CASE:**
   ```
   "ClassName: описание поведения на английском"
   ```
   Имя описывает ПОВЕДЕНИЕ, не реализацию. Хорошо: "PIController: fast convergence gives growth > 1". Плохо: "test_compute_multiplier_case1".

   **Теги Catch2 (4 обязательных):**
   ```
   "[unit][levelN][module][ClassName]"
   ```
   Пример: `"[unit][level0][reservoir][PIController]"`.

   **Структура файла:**
   ```cpp
   #include <catch2/catch_test_macros.hpp>
   #include <catch2/catch_approx.hpp>
   #include "path/to/TestedClass.h"

   using namespace project_namespace;
   using Catch::Approx;

   // helper-функции для создания объектов (static, в начале файла)
   static TestedClass make_default() { ... }

   // Тесты: конструкторы → методы → граничные случаи → инварианты
   TEST_CASE("ClassName: ...", "[unit][levelN][module][ClassName]") {
       // Arrange
       auto obj = make_default();
       // Act
       auto result = obj.Method(input);
       // Assert
       CHECK(result == expected);
   }
   ```

   **Числа с плавающей точкой:**
   - Всегда `Approx` с явным `margin` или `epsilon`, никогда `==`.
   - `CHECK(value == Approx(expected).margin(1e-12))` для абсолютной точности.
   - `CHECK(value == Approx(expected).epsilon(1e-6))` для относительной.
   - Для NaN: `CHECK(std::isnan(value))`.

   **Статическое состояние:**
   - Если класс зависит от глобального/статического состояния — инициализируй его явно в начале КАЖДОГО теста через helper-функцию.
   - Не полагайся на порядок выполнения тестов.

   **Размер тестовых данных:**
   - Минимальные структуры: 2–4 ячейки для сеток, 2–3 элемента для коллекций.
   - Цель: весь уровень выполняется < 5 секунд.

3. **Сборка и запуск:**
   ```
   cmake --build build --config Release
   ctest --test-dir build -C Release -R "<project>_unit_levelN" --output-on-failure
   ```

4. **Исправление**: если тесты не собираются или падают:
   - Ошибка компиляции → исправь тест (не продакшн-код).
   - Тест падает на CHECK → разберись, это баг в тесте или в коде. Если в тесте — исправь тест. Если в коде — сообщи мне, не исправляй продакшн-код самостоятельно.
   - Неинициализированные поля в default-конструкторе → убери CHECK для этого поля, добавь комментарий.

5. **Отчёт**: после прохождения всех тестов уровня — краткий итог:
   - Сколько файлов, сколько TEST_CASE, время выполнения.
   - Найденные проблемы (неинициализированные поля, неожиданное поведение).

Переходи к следующему уровню только после того, как текущий полностью зелёный.

### ФАЗА 4: ФИНАЛИЗАЦИЯ

После реализации всех уровней:

1. **Полный прогон:**
   ```
   ctest --test-dir build -C Release --output-on-failure
   ```
   Убедись, что ВСЕ тесты (юнит + существующие интеграционные) проходят.

2. **VS Code интеграция:**
   Настрой `.vscode/settings.json` для иерархического отображения тестов через расширение C++ TestMate (`matepek.vscode-catch2-test-adapter`):
   ```json
   {
       "cmake.ctest.testExplorerIntegrationEnabled": false,
       "testMate.cpp.test.advancedExecutables": [
           {
               "pattern": "build/Release/<project>_unit_level*.exe",
               "testGrouping": {
                   "groupByExecutable": {
                       "label": "${filename}",
                       "groupByRegex": {
                           "regexes": ["^(.*?): "],
                           "label": "${match}"
                       }
                   }
               }
           }
       ]
   }
   ```
   Добавь `.vscode/extensions.json` с рекомендацией TestMate.
   Обнови `.gitignore`: `.vscode/*` + `!.vscode/settings.json` + `!.vscode/extensions.json`.

3. **Коммиты:** один коммит на уровень, формат:
   ```
   test: юнит-тесты уровня N — ClassName1, ClassName2, ...
   ```

4. **Итоговая сводка:**
   - Общее количество тестов.
   - Покрытие: какие классы покрыты, какие пропущены и почему.
   - Найденные проблемы в продакшн-коде (если были).
   - Время выполнения всех юнит-тестов.

### ОГРАНИЧЕНИЯ

- Не модифицируй продакшн-код без моего явного разрешения.
- Не добавляй моки и фейки — тестируй реальные классы с минимальными входными данными.
- Не создавай временные файлы, не обращайся к сети или БД из тестов.
- Если Catch2 ещё не подключён к проекту — подключи через FetchContent (v3.8.0+).
- Если тестовый фреймворк уже есть (Google Test, Boost.Test и др.) — используй его вместо Catch2, адаптируй конвенции.
- Каждый тестовый файл тестирует ровно один класс (или тесно связанную группу: Segment + WellJob).
- Имена TEST_CASE на английском языке.
