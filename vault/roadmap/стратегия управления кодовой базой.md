# Стратегия управления кодовой базой

## Принципы

### 1. Vault — единственный источник правды
- Все архитектурные решения фиксируются в `knowledge/decisions/`
- Все баги — в `knowledge/debugging/` + реестр в `roadmap/известные баги и технический долг`
- Roadmap — в `roadmap/`, не в TODO-комментариях и не в issues
- Сессии — в `sessions/`, с датой и кратким slug

### 2. Изоляция изменений
- Одна фаза = одна область. Не смешивать физику, рефакторинг и оптимизацию в одной сессии.
- Каждая сессия начинается с чтения `текущие приоритеты.md` и заканчивается его обновлением.
- Крупные изменения — через промпт-файл (prompt-*.md) для воспроизводимости.

### 3. Backward compatibility
- Новый функционал при отключённых параметрах (c=0, flag=false) даёт прежний результат.
- Тест на backward compatibility обязателен при расширении физики.
- Формат CSV-выхода не менять без миграции скриптов визуализации.

### 4. Ветвление
- `main` — стабильная ветка, все тесты проходят
- Крупные изменения (новая физика, рефакторинг ядра) — в feature-ветке
- Merge в main только при 100% тестов

### Новые папки

#### `roadmap/`
Документы стратегического уровня: долгосрочный план, реестр багов и долга, стратегии.
**Когда обновлять:** при завершении фазы, обнаружении нового бага, принятии стратегического решения.

#### `knowledge/testing/`
Методология тестирования: какие тесты для каких классов, стратегия покрытия.
**Когда создавать заметку:** при написании нового уровня тестов, обнаружении непокрытой области.

#### `knowledge/performance/`
Результаты профилирования, конфигурации солвера, бенчмарки.
**Когда создавать заметку:** при профилировании, смене конфигурации AMGCL/CPR, сравнении performance.

#### `knowledge/architecture/`
API-контракты, паттерны проектирования, зависимости между модулями.
**Когда создавать заметку:** при рефакторинге, выделении нового класса, изменении API.

## Контроль развития

### Перед каждой сессией
1. Прочитать `текущие приоритеты.md`
2. Определить фазу и конкретную задачу из roadmap
3. Проверить, нет ли блокирующих багов

### В конце каждой сессии
1. Обновить `текущие приоритеты.md`
2. Создать заметку в `sessions/`
3. Если принято решение → `knowledge/decisions/`
4. Если найден баг → `knowledge/debugging/` + обновить реестр
5. Если изменена производительность → `knowledge/performance/`

### При завершении фазы
1. Обновить roadmap (чекбоксы, новый snapshot метрик)
2. Обновить инвентаризацию кодовой базы
3. Обновить стратегию тестирования (матрица покрытия)
4. Архивировать промпт-файлы сессий
