# amgcl: iluk(k=1) — новый оптимум relaxation

## Решение

Заменить `ilu0` на `iluk(k=1)` в качестве relaxation в AMG-прекондиционере.

Новая конфигурация: `amg<aggregation, iluk(k=1)> + lgmres(M=15, K=3)`.

## Обоснование

Перебор 21 конфигурации (серии D/F/G/E) на полном production-сценарии (51×51×4, 7 скважин, 730 дней):

- **iluk(k=1)**: 8.3 iters/solve, 75 с — **лучший результат**, ускорение 1.81× vs Phase 0
- ilu0: 13.3 iters/solve, 84 с — Phase 1 оптимум, 1.62× vs Phase 0
- damped_jacobi + gmres: 31.6 iters/solve, 136 с — Phase 0 baseline

Дополнительное ускорение Phase 1b vs Phase 1: –11% по полному времени (84 → 75 с).

ILU(k=1) допускает fill-in level 1 (заполнение в позициях (i,j), где существует путь i→m→j длины 2 через структуру исходной матрицы). Это даёт более точное неполное разложение при умеренных затратах на память и setup.

## Что не работает

- `ilut` (пороговый ILU) — 165 с, в 2× хуже baseline. Пороговая стратегия плохо подходит для блочного 2×2 бэкенда.
- `ilu0(damping=0.8)` — 92 с, хуже без демпфирования. Демпфирование ILU не имеет смысла при хорошей сходимости.
- Увеличение pre/post-сглаживания (npre=2, npost=2) — снижает итерации до 9.4, но время 85.5 с (каждое сглаживание дорогое).
- W-цикл — 9.8 iters, но 89 с (двойной проход по грубым уровням дорогой).

## Что не влияет

- `over_interp` (1.0–3.0): < 1% разницы по итерациям
- lgmres M > 15: M=30 не даёт ускорения с хорошим прекондиционером
- lgmres K (1–5): слабое влияние

## Применение в production

```cpp
#include <amgcl/relaxation/iluk.hpp>

using Solver_AMG = amgcl::make_solver<
    amgcl::amg<BBackend<B>, amgcl::coarsening::aggregation, amgcl::relaxation::iluk>,
    amgcl::solver::lgmres<BBackend<B>>
>;
```

Параметр `k` по умолчанию = 1. Увеличение `k` даёт ещё более точное разложение, но с O(nnz²) ростом fill-in.
