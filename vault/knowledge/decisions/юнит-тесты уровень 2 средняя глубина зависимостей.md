# Юнит-тесты: уровень 2 — средняя глубина зависимостей

Классы этого уровня зависят от типов уровней 0–1. Для тестирования нужно создать вспомогательные объекты (Segment, WellJobTime, маленькие графы связности), но не требуется полноценный симулятор.

Связано: [[граф зависимостей классов gdm_core]], [[юнит-тесты уровень 0 нулевые зависимости]], [[юнит-тесты уровень 1 зависимости от уровня 0]]

## 1. AccumulatedPerforations

**Файл:** `Reservoir/Well/SetOfPoints.h` (строки 142–172), `Reservoir/Well/SetOfPoints.cpp`

**Пространство имён:** `set_of_points`

**Зависимости:**
- Уровень 0: `Segment`, `WellJob`, `WellJobTime`
- Уровень 1: `SetOfPerforations`, `SetOfPoints`

**Описание:** Хранит полную историю перфораций скважины: последовательность `SetOfPerforations` во времени. Позволяет запрашивать конфигурацию перфораций на произвольный момент `t`.

**Что тестировать:**

### Конструкторы
- `AccumulatedPerforations()` — дефолтный, пустой
- `AccumulatedPerforations(WellJobTime)` — одна начальная перфорация

### AddNewJob — последовательность операций
- Открытие [10,30] в t=100, открытие [20,40] в t=200 → на t=200 суммарная длина = 30
- Открытие [10,30] в t=100, закрытие [10,30] в t=200 → на t=200 длина = 0
- Ошибка при добавлении операции с `t < последний t` → exception `eAccumulatedPerforations_AddNewJob`

### Геттеры дат
- `EarliestJobDate()` — дата первой операции
- `LatestJobDate()` — дата последней операции
- `AllJobMoments()` — вектор всех дат
- `NextJobMoment(t)` — ближайший момент следующей операции после `t`

### getPerforations(time)
- Запрос на `t < EarliestJobDate()` → начальная конфигурация (пустая или от первого job)
- Запрос на `t` между двумя job → конфигурация на предыдущий момент
- Запрос на `t == LatestJobDate()` → последняя конфигурация

### getPerforations_future(time)
- Конфигурация перфораций «на будущее» для данного момента

### RemoveRedundantJobs
- Удаление дублирующих операций, не меняющих конфигурацию

**Примерные тесты:**
```cpp
AccumulatedPerforations ap(WellJobTime(10.0, 30.0, true, 100.0));
CHECK(ap.EarliestJobDate() == 100.0);

ap.AddNewJob(WellJobTime(20.0, 40.0, true, 200.0));
CHECK(ap.LatestJobDate() == 200.0);

auto& perfs_150 = ap.getPerforations(150.0);
CHECK(perfs_150.TotalLength() == 20.0); // только первый [10,30]

auto& perfs_250 = ap.getPerforations(250.0);
CHECK(perfs_250.TotalLength() == 30.0); // [10,40] — объединение
```

## 2. MER_Data

**Файл:** `Descriptors/MER_Descriptor.h`, `Descriptors/MER_Descriptor.cpp`

**Пространство имён:** `reservoir_simulator::mer_descriptor`

**Зависимости:**
- Уровень 0: `WellName` (wstring), `SingleMERrecord` (map<wstring, float>)
- defines.h: `FluidDebit`, `TimeFrame`

**Описание:** Данные МЭР (Monthly Exploitation Report) для одной скважины в одном горизонте. Хранит историю добычи `MER_records` и вычисляет дебит на произвольный момент `t` через `identify_cur_MER_record`.

**Что тестировать:**

### Конструктор
- `MER_Data(name, data)` — создание с именем скважины и набором записей
- Пустой набор записей → `recordsSize() == 0`

### identify_cur_MER_record / debitPartial
- 3 записи: t=0 (oil=10, water=5), t=30 (oil=8, water=7), t=60 (oil=6, water=9)
- Запрос `debitPartial(15)` → дебит из первой записи (t=0)
- Запрос `debitPartial(45)` → дебит из второй записи (t=30)
- Запрос `debitPartial(0)` → первая запись

### knownExploitationPeriod
- `firstRecordDate()` == время первой записи
- `lastRecordDate()` == время последней записи
- `knownExploitationPeriod()` → `{firstRecordDate() - monthGap, lastRecordDate()}`

### CleanMER_record
- Удаление записей с нулевым общим дебитом в начале/конце
- Записи в середине с нулём — сохраняются

### MER_record_time_interval
- Длина текущего MER-периода = `endOfCurPeriod - beginOfCurPeriod`

**Подготовка данных для теста:**
```cpp
using SMR = std::map<std::wstring, float>;
SingleWell_MER_Data data;
data.push_back(SMR{{L"time", 0}, {L"oil_v", 10}, {L"water_v", 5},
    {L"oil_m", 8000}, {L"water_m", 5000}, {L"pump_water", 5},
    {L"idle_time", 0}, {L"type", 1}, {L"is_work", 1}});
data.push_back(SMR{{L"time", 30}, {L"oil_v", 8}, {L"water_v", 7},
    {L"oil_m", 6400}, {L"water_m", 7000}, {L"pump_water", 7},
    {L"idle_time", 0}, {L"type", 1}, {L"is_work", 1}});

MER_Data mer(L"WELL_1", data);
```

## 3. NumericalParameters

**Файл:** `Reservoir/NumericalParameters.h`, `Reservoir/NumericalParameters.cpp`

**Зависимости:**
- Уровень 0: `PIController`, `PIControllerParams`
- defines.h: `WellName`

**Описание:** Параметры численной схемы симулятора: допуски Ньютона, AMG, адаптивный шаг. Управляет увеличением/уменьшением шага `schemeTau`, подсчётом wasted trials, интеграцией с PI-контроллером.

**Что тестировать:**

### Конструкторы
- `NumericalParameters(1e-4, 12, 1e-2, 1e-2)` → `NewtonTol() == 1e-4`, `MaxNewtonIterationNmbr() == 12`
- `NumericalParameters()` — дефолтный

### increase/decrease_schemeTau
- `set_initial_schemeTau(10.0)`, `increase_schemeTau()` → `CurrentSchemeTau() > 10.0` (×(1+factor), factor=0.15)
- `decrease_schemeTau()` → `CurrentSchemeTau() < 10.0` (×(1-factor))
- Множественное уменьшение: шаг уменьшается каждый раз

### update_currentMoment
- `set_currentMoment(0)`, `set_initial_schemeTau(10)`, `update_currentMoment()` → `CurrentTimeMoment() == 10.0`

### IsNewtonIterationContinue
- `currentNewtonIterationCount < MaxNewtonIterationNmbr` → true
- После достижения максимума → false

### PI-контроллер toggle
- `SetUsePIController(true)` → `UsesPIController() == true`
- `SetPIControllerParams(params)` — параметры подхватываются, `max_iters` заменяется на `newtonMaxIterNmbr`

### update_currentAMGState
- Из tuple `{iters, error, converged}` обновляются `AMG_currentIterationCount`, `AMG_curError`, `AMG_isIterationSuccessfull`

### update_isSuccesfullNewtonTrial
- `update_isSuccesfullNewtonTrial(true)` при `CurrentANG_IsAccuracyReached()` → `IsSuccessfullNewtonTrial() == true`
- Побочный эффект: `currentNewtonIterationCount` инкрементируется

**Примерные тесты:**
```cpp
NumericalParameters np(1e-4, 12, 1e-2, 1e-2);
CHECK(np.NewtonTol() == 1e-4);
CHECK(np.MaxNewtonIterationNmbr() == 12);

np.set_initial_schemeTau(10.0);
np.increase_schemeTau();
CHECK(np.CurrentSchemeTau() > 10.0);

np.decrease_schemeTau();
np.decrease_schemeTau();
CHECK(np.CurrentSchemeTau() < 10.0);
```

## 4. CRSStructure

**Файл:** `Solver/Math/CRSStructure.h`, `Solver/Math/CRSStructure.cpp`

**Зависимости:** `<vector>`, `<cstddef>` — фактически только STL. Логически связан со SparsityPattern, но не зависит от него.

**Пространство имён:** `reservoir_simulator::linear_problem`

**Описание:** Layout-абстракция для CRS-матрицы. Строит структуру (row/col/diag/offdiag) для заданного графа связности, количества уравнений на ячейку (`eqNmbr=2` для двухфазной) и порядка переменных (`Layout`). Три варианта: `InterleavedSwP` ([Sw0,P0,...]), `InterleavedPSw` ([P0,Sw0,...]), `Blocked` ([P0,...,PN,Sw0,...,SwN]).

**Что тестировать:**

### Конструктор на маленьком графе
- 3 ячейки: `0↔1, 1↔2` (цепочка), `eqNmbr=2`, `blockPattern = {true,true,true,true}` (full 2×2)
- Проверить: `Row()` имеет `3*2 + 1 = 7` элементов
- `Col()` содержит правильные индексы столбцов
- `DiagBlocks()` — индексы диагональных блоков в массиве значений
- `TotalBlocks()` == 3 (diag) + 2*2 (offdiag) = 7

### Layout::InterleavedSwP vs InterleavedPSw
- Одинаковый граф, разные Layout → разный порядок в Col()
- `GlobalIndex(cell=1, var=0)` → для SwP: `2`, для PSw: `3`
- `GlobalIndex(cell=1, var=1)` → для SwP: `3`, для PSw: `2`

### UnpackCorrections
- Вектор corrections в CRS-порядке → physical-порядок после UnpackCorrections
- Для InterleavedPSw: corrections[2]=P1, corrections[3]=Sw1 → physical = {Sw1, P1}

### Граничные случаи
- 1 ячейка, 0 соседей → только диагональный блок
- Несимметричный blockPattern: `{true,false,true,true}` → меньше nnz_per_block

**Примерные тесты:**
```cpp
// 3 ячейки: 0-1, 1-2
std::vector<std::vector<int>> graph = {{1}, {0, 2}, {1}};
std::vector<bool> pattern = {true, true, true, true};

CRSStructure crs(Layout::InterleavedPSw, 2, 3, graph, pattern);
CHECK(crs.Row().size() == 7); // 3*2 + 1
CHECK(crs.EqNmbr() == 2);
CHECK(crs.NnzPerBlock() == 4);

// GlobalIndex для cell 1
CHECK(crs.GlobalIndex(1, 0) == 2); // var 0 → row depends on layout
```

## 5. SparsityPattern

**Файл:** `Solver/Math/SparsityPattern.h`, `Solver/Math/SparsityPattern.cpp`

**Зависимости:** `<vector>`, `<iomanip>` — фактически только STL.

**Пространство имён:** `reservoir_simulator::linear_problem`

**Описание:** Старая (до Layout-абстракции) реализация CRS-паттерна. Строит row/col/diagBlocks/offDiagBlocks для заданного графа связности. Используется как fallback или для legacy-кода.

**Что тестировать:**

### Конструктор с blockPattern
- `SparsityPattern(2, 3, graph, {true,true,true,true})`
- `TotalNmbrOfBlocks()`, `Row()`, `Col()`, `DiagBlocks()`, `OffDiagBlocks()`

### Конструктор без blockPattern
- `SparsityPattern(2, 3, graph)` — full block по умолчанию

### Проверка на маленьком графе (2×2)
- 4 ячейки, 2×2: `graph = {{1,2},{0,3},{0,3},{1,2}}`
- Симметрия: каждая ячейка имеет 2 соседа → `blocksPerRow[l] == 3` (1 diag + 2 off-diag)

### NmbrOfNonzerosPerUnitBlock
- Для pattern `{true,true,true,true}` → 4
- Для pattern `{true,false,false,true}` → 2

## 6. AbstractCells (иерархия ячеек)

**Файл:** `Solver/Grids/Cells/AbstractCells.h`

**Зависимости:** `<vector>`, `<array>`, `<algorithm>` — только STL. Header-only (кроме AbstractCells.cpp для static member init).

**Пространство имён:** `reservoir_simulator::cell`

**Описание:** Иерархия ячеек:
- `SomeDimCell(center, size)` → `Volume()`, `Dim()`
- `Dim1Cell → Dim2Cell → Dim3Cell` — добавляют X/Y/Z(), StepX/Y/Z()
- `TimeDependentCell(initState)` — хранит предыдущее состояние
- `PhysPropCell(constProps, varProps)` — физические свойства
- `SomeProcessCell_TimeDependent<Dim3Cell>` — множественное наследование, методы `AcceptState()`, `ReverseState()`, `UpdateState()`

**Что тестировать:**

### SomeDimCell / Dim3Cell
- `Dim3Cell({1,2,3}, {10,20,5})` → `X()==1, Y()==2, Z()==3, StepX()==10, StepY()==20, StepZ()==5, Volume()==1000`

### PhysPropCell
- Чтение `GetVariableFieldProperties()` после конструирования

### SomeProcessCell_TimeDependent (через минимальную конкретную реализацию)
- Для тестирования нужна конкретная реализация (не абстрактный класс). Можно использовать `TwoPhaseFlowCell` (уровень 3) или создать mock-класс.
- `AcceptState()` → `ReverseState()` восстанавливает предыдущее состояние
- `UpdateState(corrections)` → `VariableFieldProperties += corrections`
- `AcceptState()` → `UpdateState()` → `ReverseState()` → состояние = до UpdateState

**Примерные тесты:**
```cpp
Dim3Cell cell({1.0, 2.0, 3.0}, {10.0, 20.0, 5.0});
CHECK(cell.X() == 1.0);
CHECK(cell.Y() == 2.0);
CHECK(cell.Z() == 3.0);
CHECK(cell.Volume() == 1000.0);
CHECK(cell.StepX() == 10.0);
CHECK(cell.StepY() == 20.0);
CHECK(cell.StepZ() == 5.0);
```

## Порядок реализации

1. **CRSStructure** — центральный для солвера, чистая логика
2. **SparsityPattern** — аналогичен CRSStructure, можно параллельно
3. **AbstractCells (Dim3Cell)** — геометрия ячеек, быстро
4. **AccumulatedPerforations** — скважинная логика
5. **NumericalParameters** — параметры схемы
6. **MER_Data** — данные МЭР (требует подготовки тестовых данных)
