# /plan — составить детализированный план решения задачи

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `BUG-001`, `DEBT-007`) или URL GitHub issue (например `#1`).

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

---

## Фаза 1: Сбор контекста

### 1.1. Загрузить задачу

1. Найди запись в `vault/GDM/roadmap/известные баги и технический долг.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM`
3. Прочитай подробную заметку из `knowledge/debugging/` или `knowledge/decisions/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.2. Загрузить связанные заметки

1. Из подробной заметки найди все wiki-ссылки `[[...]]`
2. Прочитай каждую связанную заметку (physics, numerics, decisions)
3. Проверь, есть ли связанные BUG/DEBT — прочитай их тоже
4. Прочитай `vault/GDM/roadmap/стратегия тестирования GDM.md` — понять текущие паттерны тестов

### 1.3. Исследовать код

Для каждого файла, упомянутого в задаче:

1. **Валидация:** проверь, что файл существует, строки актуальны
2. **Контекст:** Read окрестности ±30 строк от проблемного места
3. **Вызовы вверх:** grep — кто вызывает проблемную функцию?
4. **Вызовы вниз:** что вызывается из проблемного кода?
5. **Параллельные структуры:** есть ли аналогичный паттерн (AcceptState/ReverseState для ячеек → нужен ли для скважин?)
6. **Существующие тесты:** grep по именам функций в `tests/` — что уже покрыто?
7. **Инварианты:** какие свойства должны соблюдаться? (монотонность, баланс масс, знаковые конвенции)

## Фаза 2: Анализ и проработка

### 2.1. Варианты решения

Для каждого варианта (минимум 2, обычно 3):
- **Суть** — что именно менять, в каких файлах
- **Конкретные изменения** — псевдокод или diff-like описание для каждого файла
- **Плюсы/минусы** — trade-offs
- **Риски** — что может пойти не так
- **Совместимость** — ломает ли что-то существующее?

### 2.2. Выбор варианта

Обоснуй выбор. Если варианты комбинируются — объясни порядок и зависимости.

### 2.3. Поиск подводных камней

Для выбранного варианта проверь каждый пункт:

1. **Побочные эффекты:** затронутые функции вызываются из других мест — сломается ли что-то?
2. **Потокобезопасность:** код использует OpenMP — безопасны ли изменения?
3. **Граничные случаи:** нулевые значения, пустые контейнеры, деление на ноль, NaN propagation
4. **Производительность:** добавляются ли аллокации в горячий путь? Копирование в цикле?
5. **Обратная совместимость:** изменится ли поведение для сценариев, которые сейчас работают?
6. **Порядок вызовов:** зависит ли от порядка инициализации? Что если вызвать раньше/позже?
7. **Состояние при ошибке:** если Newton не сошёлся на первой итерации — есть ли что откатывать?
8. **Численная устойчивость:** tolerance-ы, absolute vs relative, overflow/underflow
9. **Связь с другими багами:** не конфликтует ли фикс с обходами других BUG (например BUG-002 workaround в amgcl)?

### 2.4. Обнаружение новых проблем

В ходе анализа могут обнаружиться новые баги или технический долг. Для каждого:
1. Зафиксируй в отдельном списке (в плане, раздел «Обнаруженные проблемы»)
2. Определи: блокирует ли текущую задачу?
3. Если блокирует — включи в план. Если нет — после завершения плана добавь в `известные баги и технический долг.md`

## Фаза 3: Детализация плана

### 3.1. Структура плана

План разбивается на **шаги**. Каждый шаг — атомарная единица работы, которую можно выполнить и проверить независимо.

Для каждого шага:

```
### Шаг N: <название>

**Файлы:** <список файлов для изменения>

**Что сделать:**
1. Конкретное действие с указанием файла, функции, строк
2. Конкретное действие...

**Псевдокод / описание изменений:**
(diff-like или развёрнутое описание — достаточное для реализации без дополнительного контекста)

**Проверка:**
- Как убедиться, что шаг выполнен правильно
- Какой тест запустить
- Что должно измениться в поведении

**Подводные камни:**
- На что обратить внимание при реализации

**Зависимости:**
- От каких шагов зависит
- Какие шаги зависят от этого
```

### 3.2. Порядок шагов

Шаги группируются в этапы:

1. **Подготовка** — создать ветку, настроить тесты, убедиться что всё собирается
2. **Минимальный фикс** — чтобы проблема перестала проявляться
3. **Тесты для минимального фикса** — проверить что фикс работает, снять скрытые теги
4. **Архитектурное решение** — правильная реализация
5. **Тесты для архитектуры** — unit + integration + regression
6. **Верификация** — сравнение с аналитикой, баланс масс, визуальная проверка
7. **Очистка** — удалить workaround-ы если стали не нужны, обновить vault

### 3.3. Тестовая стратегия

Для каждого шага определи тесты:

- **Unit-тесты:** изолированные тесты новых/изменённых функций
- **Regression-тесты:** существующие тесты, которые не должны сломаться
- **Integration-тесты:** сценарии, которые задействуют фикс в контексте
- **Инвариантные проверки:** баланс масс, монотонность, Sw ∈ [0,1], P > 0
- **Visual verification:** CSV export + анимация для ключевых сценариев

Формат теста:
```
**Тест:** <название теста Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp
**Сценарий:** <что проверяем>
**Ожидаемый результат:** <конкретные числа или условия>
```

## Фаза 4: Верификация плана (3 раунда)

### Раунд 1: Полнота

Перечитай план целиком и проверь:
- [ ] Каждый файл из «Затронутые файлы» упомянут хотя бы в одном шаге
- [ ] Для каждого шага есть проверка (тест или ручная)
- [ ] Зависимости шагов не образуют циклов
- [ ] Нет шагов без зависимостей, которые висят в воздухе
- [ ] Все обнаруженные подводные камни (фаза 2.3) адресованы в конкретных шагах
- [ ] Тестовая стратегия покрывает: happy path, edge cases, regression

### Раунд 2: Корректность

Для каждого шага:
- [ ] Псевдокод/описание изменений реализуемо — нет обращений к несуществующим методам, полям
- [ ] Типы совместимы (проверь grep-ом по объявлениям)
- [ ] Новый код не противоречит существующим инвариантам
- [ ] Порядок вызовов корректен (инициализация до использования)

### Раунд 3: Автономность

Представь, что план читает разработчик, который:
- Не имеет контекста этой сессии
- Видит проект впервые
- Работает с compact-сжатым контекстом

Проверь:
- [ ] Каждый шаг самодостаточен — не ссылается на «то, что обсуждали выше»
- [ ] Файлы указаны с полными путями от корня проекта
- [ ] Номера строк актуальны (верифицированы grep-ом на фазе 1.3)
- [ ] Объяснено ПОЧЕМУ делается каждое изменение, а не только ЧТО
- [ ] Физический/математический контекст дан там, где нужен (формулы, ссылки на vault-заметки)
- [ ] Термины расшифрованы при первом упоминании

Если раунд верификации обнаруживает проблемы — исправь план и повтори раунд.

## Фаза 5: Сохранение

### 5.1. Создать файл плана

Сохрани в `vault/GDM/plans/<ID-lowercase> <slug>.md`:

```
vault/GDM/plans/bug-001 well-state-rollback.md
vault/GDM/plans/debt-007 amgcl-fetchcontent.md
```

Создай папку `vault/GDM/plans/` если не существует.

Frontmatter плана:
```yaml
---
tags:
  - план
  - <тип: баг | рефакторинг | фича>
date: <дата создания>
issue: <ID>
github: <номер issue или null>
status: готов к реализации
---
```

### 5.2. Обновить связи

1. В записи техдолга добавь поле `- **План:** [[<имя файла плана>]]`
2. В GitHub issue (если есть) добавь комментарий со ссылкой на план:
   ```
   gh issue comment <N> --repo ArturSalamatin/GDM --body "План решения подготовлен: vault/GDM/plans/<файл>"
   ```
3. Обнови `vault/GDM/00-home/index.md` — добавь секцию Plans если нет

### 5.3. Зафиксировать новые проблемы

Для каждой проблемы, обнаруженной на фазе 2.4:
1. Добавь запись в `известные баги и технический долг.md` с новым ID
2. Если проблема существенная — создай заметку в `knowledge/debugging/` или `knowledge/decisions/`

### 5.4. Сообщить результат

Выведи:
- Путь к файлу плана
- Количество шагов и этапов
- Обнаруженные новые проблемы (если есть)
- Рекомендуемое имя ветки
- Оценку сложности (количество файлов, строк изменений)

---

## Примечания

- Не создавай коммитов — только файлы в vault. Пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Файл плана должен быть ДЛИННЫМ и ПОДРОБНЫМ — это его главное свойство. Лучше избыточность, чем недосказанность
- Каждый шаг должен быть реализуем за один присест (не более 30 минут работы)
- Если задача слишком большая (>15 шагов) — предложи разбить на под-задачи, каждая со своим планом
