# /plan-research — план численного эксперимента

Аргумент: `$ARGUMENTS` — идентификатор эксперимента (например `RES-001`, `RES-004`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

Ключевое отличие от других plan-команд: результат исследования — **вывод** (подтвердить/отвергнуть гипотезу), а не код в main. Код может появиться как следствие, но план не обязан заканчиваться merge.

---

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/GDM/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/GDM` → из title извлеки ID (формат: `RES-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/GDM/roadmap/исследования и эксперименты.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM`
3. Прочитай связанные заметки из `knowledge/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Определить подтип

| Подтип | Признак | Пример |
|---|---|---|
| **Схема/метод** | альтернативная дискретизация, солвер, прекондиционер | RES-001: upstream vs TVD |
| **Параметрическое исследование** | варьирование параметров, чувствительность | RES-004: PI-контроллер |
| **Архитектурное сравнение** | IMPES vs FI, блочный vs скалярный | RES-002: IMPES vs FI |
| **Физический эффект** | влияние нового члена уравнения | RES-005: капиллярное давление |

### 1.4. Извлечь имя ветки

1. Из GitHub issue или vault-записи
2. Если нет — сгенерируй: `research/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.5. Загрузить связанные заметки

1. Wiki-ссылки из записи — прочитать каждую
2. `vault/GDM/atlas/математическая модель двухфазной фильтрации.md` — текущая мат. модель
3. `vault/GDM/atlas/численные методы решения уравнений фильтрации.md` — текущие численные методы
4. `vault/GDM/knowledge/numerics/` и `vault/GDM/knowledge/physics/` — связанные заметки
5. `vault/GDM/roadmap/стратегия тестирования GDM.md` — паттерны тестов
6. `vault/GDM/roadmap/инвентаризация кодовой базы*.md` — какие модули затронуты
7. Зависимости: блокирующие BUG/DEBT/FEAT/VAL

### 1.6. Исследовать код

1. **Что менять:** какой модуль/алгоритм является предметом исследования
2. **Где варьировать:** параметры, которые нужно менять для эксперимента
3. **Как измерять:** профилирование, CSV export, логи Newton
4. **Существующие бенчмарки:** grep в `tests/` и examples
5. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности» — production-код, API, тесты, которые эксперимент не должен затрагивать

## Фаза 2: Проектирование эксперимента

### 2.1. Формулировка гипотезы

Гипотеза должна быть фальсифицируемой:
- **Гипотеза:** <одно предложение>
- **Нулевая гипотеза (H0):** <что означает «не подтвердилось»>
- **Критерий:** <при каком результате гипотеза принимается/отвергается>

### 2.2. Дизайн эксперимента

1. **Контрольный сценарий (baseline):** текущая реализация, зафиксированные параметры
2. **Экспериментальный сценарий:** что меняем (один фактор за раз!)
3. **Варьируемые параметры:** какие значения, сколько точек
4. **Фиксированные параметры:** что остаётся постоянным
5. **Повторяемость:** если есть стохастика (порядок итераций OpenMP) — сколько повторов

### 2.3. Метрики

Для каждой метрики:
- Что измеряем (wall-clock, Newton iterations, L2 error, front width)
- Как считаем (таймер, CSV analysis, Python-скрипт)
- Формат вывода (таблица, график, heatmap)

### 2.4. Математическое обоснование

Для подтипов «Схема/метод» и «Физический эффект»:
1. Уравнения текущей и альтернативной схемы
2. Теоретические свойства (порядок аппроксимации, устойчивость, монотонность)
3. Ожидаемое поведение из теории
4. Ссылки на литературу

### 2.5. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Изоляция фактора:** меняем ровно одну вещь, остальное фиксировано
- [ ] **Baseline воспроизводим:** повторный запуск даёт те же результаты
- [ ] **Масштаб сетки:** результаты на мелкой сетке могут не переноситься на крупную
- [ ] **Численные артефакты:** не путаем физический эффект с численной диффузией/дисперсией
- [ ] **Время прогона:** оценить wall-clock для всех точек (не запустить серию на 10 часов)
- [ ] **Блокирующие баги:** не ломает ли BUG-NNN интерпретацию результатов
- [ ] **Зависимости:** нужна ли FEAT-NNN для эксперимента

### 2.6. Обнаружение новых проблем

Зафиксировать, определить блокирует ли, включить в план или отложить.

## Фаза 3: Детализация плана

### 3.1. Этапы эксперимента

1. **Подготовка** — ветка, зелёные тесты, baseline-прогон
2. **Инструментация** — добавить замеры, логирование (если нужно)
3. **Реализация альтернативы** — новая схема/параметр (в отдельном #ifdef или конфигурации)
4. **Контрольный прогон** — baseline с инструментацией, сохранить результаты
5. **Экспериментальные прогоны** — серия с варьируемыми параметрами
6. **Сбор данных** — CSV, логи → единый формат
7. **Анализ** — Python-скрипт: таблицы, графики, статистика
8. **Вывод** — подтвердить/отвергнуть гипотезу, сформулировать рекомендацию
9. **Документация** — заметка в vault с результатами, графиками, выводом
10. **Решение** — создать FEAT/VAL если подтвердилось, или закрыть как ❌ ОТВЕРГНУТО

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение

**Файлы:** <полные пути>

**Контекст:**
Для читателя без контекста: что исследуем, какая гипотеза,
что ожидаем на этом шаге.

**Что сделать:**
1. Конкретное действие
2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Сборка: `cmake --build build --config Release`
- Тесты: `ctest --test-dir build -C Release`
- Все существующие тесты зелёные (исследование не ломает main!)

**Подводные камни:**
- <ссылки на чеклист 2.5>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Формат результатов

```
## Результаты эксперимента RES-NNN

### Таблица
| Параметр | Baseline | Вариант A | Вариант B |
|---|---|---|---|
| <метрика 1> | ... | ... | ... |

### Графики
- <описание: что по осям, что показывает>
- Файлы: `vault/GDM/knowledge/<...>/<файл>.png`

### Вывод
- Гипотеза: ✅ ПОДТВЕРЖДЕНА / ❌ ОТВЕРГНУТА
- Обоснование: <2-3 предложения с цифрами>
- Рекомендация: <создать FEAT-NNN / изменить default / не делать>
```

### 3.4. Тесты (если применимо)

Если эксперимент добавляет regression-тест (например: «убедиться, что новая схема при baseline-параметрах даёт те же результаты»):

```
**Тест:** <название Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp (существующий / новый)
**Сценарий:** <что проверяем>
**Setup:** <параметры>
**Ожидание:** <конкретные числа или неравенства>
**Предотвращает:** <какой класс ошибок ловит>
```

### 3.5. Критерии завершения

- [ ] Все прогоны завершены
- [ ] Данные собраны и визуализированы
- [ ] Вывод сформулирован (подтверждена/отвергнута)
- [ ] Все существующие тесты зелёные (исследование не сломало main)
- [ ] Vault обновлён: заметка с результатами, статус в реестре
- [ ] Если подтверждено — создана запись FEAT/VAL
- [ ] GitHub issue прокомментирован с выводом, закрывается при merge (если создан)
- [ ] Roadmap фаза обновлена (если эксперимент связан с фазой)
- [ ] Экспериментальный код удалён из main (или оставлен за #ifdef с обоснованием)

### 3.6. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Прочитай мат. модель и численные методы в vault/GDM/atlas/
4. Создай ветку: `git checkout -b <branch>`
5. Собери: `cmake -B build -S . -G "Visual Studio 17 2022"; if ($?) { cmake --build build --config Release }`
6. Прогони тесты (baseline): `ctest --test-dir build -C Release`
7. Запомни количество тестов и время — это baseline
8. Начни с шага 1. После каждого шага: сборка + тесты
```

- [ ] Все подводные камни (2.5) адресованы

### Раунд 2: Корректность

Общее (для каждого шага):
- [ ] Упомянутые методы/поля/типы существуют (grep)

- [ ] Математическое обоснование (если есть): уравнения, размерности

### Раунд 3: Автономность

Представь: Claude в новой сессии с compact-контекстом.

- [ ] Каждый шаг самодостаточен
- [ ] Полные пути к файлам
- [ ] Объяснено ПОЧЕМУ, а не только ЧТО
- [ ] Гипотеза и критерий чётко сформулированы

- [ ] Термины расшифрованы
- [ ] «Как начать работу» — конкретные команды
- [ ] Baseline зафиксирован (количество тестов, время)

Из фазы 2.6 → соответствующий реестр с новыми ID.

- Путь к плану

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Ключевое: гипотеза + критерий + формат результатов — без этого эксперимент бессмысленен
- Исследование не должно ломать main — весь экспериментальный код за #ifdef или в отдельных файлах
- Если >15 шагов — разбить на под-задачи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
