# /merge – влитие ветки задачи в experimental

Аргумент: `$ARGUMENTS` – идентификатор задачи (`BUG-NNN`, `DEBT-NNN`, `FEAT-NNN`, `VAL-NNN`, `RES-NNN`). Без аргумента – задача, реализованная `/implement` в этой сессии.

Запускается только по слову пользователя: `/merge <ID>` или «мерж» после `/implement` в той же сессии – процедура одна.

Результат: ветка задачи влита в `experimental` (`--no-ff`), итог мержа проверен, worktree удалён, **ветка задачи сохранена**, vault отмечает «влит <hash>», ветка задачи и `experimental` запушены в `origin`, GitHub issue закрыт. Влитие experimental → dev → main – по-прежнему вручную пользователем.

Обозначения – как в `/implement` («Схема работы»): `<КОРЕНЬ>` = `d:\Lessons\Grants\2027\GDM` – основной каталог, `<W>` = `<КОРЕНЬ>\.worktrees\<id-lowercase>`, база – `experimental`. Мерж и коммиты – в основном каталоге, на `experimental`. Переменные PowerShell не переживают отдельный вызов инструмента – задавать в той же команде, что и использование.

## Фаза 1: Подготовка

### 1.1. Найти задачу

1. План: `<W>\vault\GDM\plans\<id-lowercase>*` (версия ветки задачи), если worktree есть; иначе `<КОРЕНЬ>\vault\GDM\plans\<id-lowercase>*`
2. Из frontmatter: `branch`, `github`, `status`, `worktree`
3. `status: реализован` – в любой из двух копий плана (задачи, начатые до worktree-правил `/implement`, вели vault в основном каталоге). Иначе – СТОП: реализация не завершена; сообщи, не продолжай без подтверждения

### 1.2. Проверки до мержа

1. **Основной каталог на `experimental`:** `git -C <КОРЕНЬ> branch --show-current`. Иначе – СТОП.
2. **Ветка не влита:** `git -C <КОРЕНЬ> log --oneline experimental..<branch>` непуст. Пуст – ветка уже в базе: СТОП, сообщи (могут оставаться фазы 4–7 – по решению пользователя).
3. **Worktree чистый:** `git -C <W> status --porcelain` пуст (игнорируемые файлы – `build\`, `results\` – не в счёт). Непуст – СТОП, покажи файлы: незакоммиченная работа, решает пользователь.
4. **Нет пересечения с незакоммиченными правками основного каталога:**
   ```powershell
   git -C <КОРЕНЬ> diff --name-only experimental...<branch>   # что меняет ветка
   git -C <КОРЕНЬ> status --porcelain                          # что не закоммичено в основном каталоге
   ```
   Пересечение непусто (включая неотслеживаемые `??`, которые ветка добавляет) – СТОП, перечисли файлы: мерж откажет («local changes would be overwritten») или смешает чужие правки с влитием. Обычно – дождаться коммита параллельной сессии; решает пользователь.

   **Исключение – общие файлы vault:** реестры `vault/GDM/roadmap/*.md`, `vault/GDM/00-home/index.md`, `vault/GDM/00-home/текущие приоритеты.md` – тот же список, что «Общие файлы vault» в шаге 1.4 `/implement`. Те из них, что попали в пересечение, закоммитить целиком, одним отдельным коммитом в `experimental`, без вопроса пользователю и не разбирая, чьи в них правки: в них только регистрация и краткие описания задач параллельных сессий, им место в базе.
   ```powershell
   git -C <КОРЕНЬ> add -- <общие файлы из пересечения>
   git -C <КОРЕНЬ> commit -m "vault: общие файлы – незакоммиченные правки основного каталога (перед влитием <ID>)" -- <общие файлы из пересечения>
   ```
   Коммит с путями берёт только эти файлы (правило 6 `/implement`). Затем повторить проверку п. 4. Остались в пересечении другие файлы – СТОП по общему правилу: планы, заметки `knowledge/`, материалы `vault/GDM/issues/` и код чужих задач без пользователя не коммитятся.
5. **Ушла ли база вперёд по коду с момента ветвления:**
   ```powershell
   $fork = git -C <КОРЕНЬ> merge-base experimental <branch>; git -C <КОРЕНЬ> diff --name-only $fork experimental -- src/ HydroSolver/ tests/ examples/ CMakeLists.txt
   ```
   Непусто – итог мержа никем не проверен: фаза 3 обязательна. Пусто – код итога мержа совпадает с проверенным на ветке, фаза 3 не нужна.
6. **Результаты задачи сохранены.** `<W>\results\` и `<W>\build\` игнорируются git и удалятся вместе с worktree. Нужные после задачи файлы (на них ссылаются план, реестр, заметки) – скопировать в `<КОРЕНЬ>\results\` до фазы 4; что копировать, спроси пользователя, если план этого не говорит.
7. **Сообщи в чат перед мержем:** ветка, база, число коммитов ветки, точка ветвления, нужна ли фаза 3, коммит общих файлов vault (п. 4), если он был, – с перечнем файлов, что скопировано в `results\` (п. 6).

### 1.3. Push ветки задачи

До мержа – ветка задачи на `origin` в том виде, в каком её вливают:

```powershell
git -C <КОРЕНЬ> push -u origin <branch>
```

Без `--force`. Отказ (ветка на `origin` разошлась с локальной, нет сети, нет доступа) – СТОП до мержа, сообщи вывод; решает пользователь.

## Фаза 2: Мерж

```powershell
git -C <КОРЕНЬ> merge --no-ff --no-edit <branch>
```

Сообщение по умолчанию – `Merge branch '<branch>' into experimental`, как у прежних влитий.

**Конфликт:**
- **Только в файлах `vault/`** – разрешить самому. В реестрах, `index.md`, планах оставить обе стороны: новые записи базы и статус с ветки. Строку, которую правили обе стороны, – свести, не выбрасывая содержание ни одной. Показать пользователю итог по каждому файлу (`git -C <КОРЕНЬ> diff -- <файл>`) **до коммита**; после согласия – `git -C <КОРЕНЬ> add -- <файлы>` и `git -C <КОРЕНЬ> commit --no-edit`.
- **В `CHANGELOG.md`, только внутри раздела «## Не выпущено»** (обе стороны дописали пункты задач, `/implement` 4.1) – разрешить самому: пункты обеих сторон сохранить дословно, сначала базы, затем ветки; одноимённые подразделы свести в один, порядок – «Добавлено», «Изменено», «Исправлено», «Удалено». Итог – пользователю до коммита, как для vault. Конфликт в другой части журнала – правило ниже.
- **Ссылка на подмодуль `amgcl`** – задачи подмодуль не меняют; конфликт по нему – СТОП, как ниже.
- **Хоть один конфликт вне `vault/`** (кроме случая с журналом) – СТОП. Мерж оставить как есть, перечислить файлы, предложить: разрешить вместе или `git merge --abort`. Решает пользователь; `--abort`, `reset`, `checkout --` – только с его разрешения.

Запомни: `<hash>` = `git -C <КОРЕНЬ> rev-parse --short HEAD`, родитель со стороны базы – `git -C <КОРЕНЬ> rev-parse --short HEAD^1`.

## Фаза 3: Проверка итога мержа

Только если база ушла вперёд по коду (1.2 п. 5).

Проверять в worktree задачи, а не в основном каталоге: в основном каталоге могут лежать незакоммиченные правки параллельных сессий, и прогон проверил бы не итог мержа. Сборка `<W>\build` уже сконфигурирована – пересобирается только изменённое.

```powershell
git -C <W> switch --detach <hash>
cmake --build <W>\build --config Release
ctest --test-dir <W>\build -C Release -R "^unit\." --output-on-failure
```

Тесты строго последовательно, без `-j`. Если база с момента ветвления меняла то, что проверяют только integration-тесты (те же признаки, что у «Регресс: полный» в планах), – полный уровень `ctest --test-dir <W>\build -C Release --output-on-failure`. Warnings в выводе сборки – как в `/implement`: новых быть не должно.

Красный – СТОП: мерж уже в `experimental` (локально), `experimental` **не пушить**. Сообщи: какие тесты, зелёные ли они по отдельности на ветке и на базе. Варианты – исправление новой задачей или откат мержа; откат (`git revert`, `git reset`) – только по решению пользователя. Worktree не удалять – он нужен для разбора.

## Фаза 4: Удаление worktree

**Сначала вывести сессию из worktree.** Фаза 3 могла оставить сессию в `<W>`. Инструменты PowerShell и Bash начинают каждую команду в каталоге, где закончилась предыдущая. Windows не удаляет каталог, который служит текущим каталогом процесса, и `git worktree remove` падает с «Permission denied». `Set-Location` этого не исправляет: он меняет путь внутри PowerShell, а не текущий каталог процесса. Каталог процесса меняет `[System.IO.Directory]::SetCurrentDirectory`.

**Затем снять подмодуль.** git не удаляет worktree с инициализированным подмодулем («working trees containing submodules cannot be moved or removed»). Подмодуль `amgcl` в worktree не правится, `deinit` ничего не теряет.

```powershell
[System.IO.Directory]::SetCurrentDirectory("<КОРЕНЬ>"); Set-Location <КОРЕНЬ>; git -C <W> status --porcelain; git -C <W> submodule deinit -f amgcl; git -C <КОРЕНЬ> worktree remove .worktrees/<id-lowercase>
git -C <КОРЕНЬ> worktree prune
git -C <КОРЕНЬ> branch --list <branch>   # ветка на месте
```

`status --porcelain` перед удалением должен быть пуст – по нему решается, можно ли удалять остаток при сбое (ниже). Если в сессии вызывался инструмент Bash, перед удалением – отдельным вызовом `cd "d:/Lessons/Grants/2027/GDM"`: его каталог тоже сохраняется между командами.

- Без `--force`. Отказ – покажи причину и жди пользователя:
  - неотслеживаемые или изменённые файлы – что это, решает пользователь;
  - Windows: файл занят процессом (терминал VS Code в каталоге worktree, оставшийся после сборки `MSBuild.exe`, открытый в редакторе файл) – попроси закрыть, повтори.
- **Сбой «Permission denied» с уже снятой регистрацией.** Git снимает регистрацию worktree до удаления файлов: `git worktree list` его не показывает, а каталог остаётся с частью дерева. Если `status --porcelain` перед удалением был пуст – в остатке только закоммиченное и игнорируемое, удалить остаток:
  ```powershell
  [System.IO.Directory]::SetCurrentDirectory("<КОРЕНЬ>"); Set-Location <КОРЕНЬ>; Remove-Item -LiteralPath "\\?\<КОРЕНЬ>\.worktrees\<id-lowercase>" -Recurse -Force; git -C <КОРЕНЬ> worktree prune
  ```
  Префикс `\\?\` – для путей длиннее 260 символов (в `build\_deps` они встречаются). Не удаляется и так – каталог держит другой процесс: попроси закрыть, повтори. `status` был непуст – не удалять, решает пользователь.
- Игнорируемые файлы worktree (`build\`, `results\`) удаляются вместе с ним – они воспроизводимы; нужное скопировано в 1.2 п. 6.
- **Ветку задачи не удалять** (`git branch -d` не выполнять): она остаётся для истории и ссылок из vault.
- `ExitWorktree` не использовать: он удаляет ветку.
- Worktree у задачи не было – фазу пропустить.

## Фаза 5: Отметка «влит» в vault

В основном каталоге, на `experimental`. После мержа в базе – vault с ветки задачи.

1. **План:** во frontmatter – `merged: <hash> (<дата>)`; в `worktree:` дописать «; удалён после влития».
2. **Реестр**, запись задачи, строка «**Статус:**»: «не влит – ветка … в `.worktrees/<id>`» → «влит <дата> (`<hash>`, поверх `<родитель>`, <без конфликтов | конфликты в vault: <файлы>, разрешены>; <итог мержа: быстрый уровень N passed | база по коду не менялась>; worktree удалён, ветка оставлена) – ветка `<branch>`».
3. **`vault/GDM/00-home/index.md`** – строка плана задачи, если в ней есть статус.
4. **Коммит** с явными путями (правило 6 `/implement`; реестр и `index.md` – общие файлы, коммитятся целиком):
   ```powershell
   git -C <КОРЕНЬ> add -- <файлы>
   git -C <КОРЕНЬ> commit -m "vault: <ID> влит (<hash>)" -- <файлы>
   ```

## Фаза 6: Push experimental

После мержа, проверки итога (фаза 3) и отметки «влит» (фаза 5) – одним push:

```powershell
git -C <КОРЕНЬ> log --oneline origin/experimental..experimental   # что уйдёт: мерж, «влит» и, возможно, коммиты параллельных сессий
git -C <КОРЕНЬ> push origin experimental
```

Список уходящих коммитов – в отчёт. Без `--force`. Отказ (на `origin` в `experimental` есть коммиты, которых нет локально) – СТОП: не `pull`, не `--force`, не `rebase`; сообщи вывод, решает пользователь. Issue (фаза 7) – только после успешного push.

## Фаза 7: Закрыть GitHub issue

Если в frontmatter плана поле `github:` отсутствует или равно `null` – пропусти фазу. Сам issue не закроется: ветка GitHub по умолчанию – `dev`, а влитие идёт в `experimental`.

```powershell
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User"); gh issue close <N> --repo ArturSalamatin/GDM --comment 'Влито в experimental: <hash> (<дата>). Ветка <branch> сохранена.'
```

Одинарные кавычки: в двойных PowerShell считает обратную кавычку экранированием.

## Примечания

- **Push – только два:** ветка задачи до мержа (1.3) и `experimental` после отметки «влит» (фаза 6). Без `--force`; отказ – СТОП
- **`dev` и `main` не трогать** – влитие experimental → dev → main делает пользователь
- **Ветку задачи не удаляй** – ни локально, ни на `origin`
- Задачи, начатые до worktree-правил `/implement` (ветка в основном каталоге, worktree нет): процедура та же, фаза 4 пропускается; в фазе 5 правки vault – поверх уже имеющихся в базе
- Язык: русский
