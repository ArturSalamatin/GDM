# /plan-feature — план реализации новой фичи

Аргумент: `$ARGUMENTS` — идентификатор фичи (например `FEAT-001`, `FEAT-004`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

---

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/GDM/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/GDM` → из title извлеки ID (формат: `FEAT-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/GDM/roadmap/планируемые фичи.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM`
3. Прочитай связанные заметки из `knowledge/` (поле **Подробности**)
4. Найди фазу в [[roadmap долгосрочный план развития GDM]] — прочитай критерии завершения фазы
5. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Определить подтип

| Подтип | Признак | Пример |
|---|---|---|
| **Физика** | новое уравнение, новый член, новая модель | FEAT-004: сжимаемость, FEAT-005: капиллярка |
| **Режим** | новый режим скважины, граничных условий | FEAT-001: BHP, FEAT-003: закрытые границы |
| **Модель** | новая расчётная формула, корреляция | FEAT-002: Peaceman WI |
| **Масштабирование** | производительность, параллелизм | FEAT-007: 100k ячеек, FEAT-008: OpenMP |
| **Инфраструктура** | ввод/вывод, CLI, визуализация | FEAT-009: JSON input |

Подтип определяет акценты на фазе 2 и шаблон этапов на фазе 3.

### 1.4. Извлечь имя ветки

1. Из GitHub issue или vault-записи (если `/issue` уже генерировал)
2. Если нет — сгенерируй: `feat/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.5. Загрузить связанные заметки

1. Wiki-ссылки из записи — прочитать каждую
2. Зависимости: фича может зависеть от BUG/DEBT/FEAT/VAL/RES
3. `vault/GDM/roadmap/стратегия тестирования GDM.md` — паттерны тестов
4. `vault/GDM/roadmap/инвентаризация кодовой базы*.md` — какие модули затронуты
5. `vault/GDM/atlas/математическая модель двухфазной фильтрации.md` — текущая мат. модель
6. `vault/GDM/knowledge/physics/` — связанные физические заметки

### 1.6. Исследовать код

1. **Точки интеграции:** где в коде новая фича должна подключаться? grep по ключевым классам/функциям
2. **Существующий API:** какие интерфейсы будут расширяться? Какие — не должны меняться
3. **Аналогичные механизмы:** есть ли в проекте похожая фича, которая может служить образцом?
4. **Тесты:** какие тесты покрывают затрагиваемые модули?
5. **Зависимости сборки:** CMakeLists.txt, include-пути
6. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности» — модули, API, поведение, которые фича не должна затрагивать

## Фаза 2: Проектирование

### 2.1. Физическое/математическое обоснование

Для подтипов «Физика», «Режим», «Модель»:

1. **Уравнения:** выписать все уравнения, которые меняются или добавляются
2. **Дискретизация:** как уравнения дискретизируются на сетке GDM
3. **Вклад в Якобиан:** какие новые слагаемые появляются в матрице, их производные
4. **Размерный анализ:** единицы измерения, согласованность с существующей системой единиц GDM (см. [[таблица единиц GDM vs MRST]])
5. **Предельные случаи:** при каких параметрах новая фича вырождается в текущую модель
6. **Литература:** ссылки на учебники/статьи (Aziz & Settari, Peaceman, Chen et al.)

Для подтипов «Масштабирование», «Инфраструктура» — пропустить, перейти к 2.2.

### 2.2. Проектирование API

1. **Новые классы/структуры:** имена, поля, ответственность
2. **Расширение существующих:** какие методы добавляются, какие сигнатуры меняются
3. **Конфигурация:** как пользователь включает/настраивает фичу (параметры, флаги)
4. **Значения по умолчанию:** при которых поведение идентично текущему (backward compatibility)
5. **Формат данных:** если фича затрагивает ввод/вывод — формат, сериализация

### 2.3. Backward compatibility

Ключевой инвариант: **при отключённом/нулевом параметре поведение идентично текущей модели.**

Конкретизировать:
- Какой параметр = 0 / false / отсутствует означает «фича выключена»
- Какие тесты это проверяют (перечислить)
- Какие существующие тесты не должны сломаться (перечислить)

### 2.4. Варианты реализации

Для каждого варианта (минимум 2):
- **Архитектура** — где новый код, как интегрируется
- **Конкретные изменения** — какие файлы, какие новые/изменённые методы
- **Промежуточные состояния** — можно ли разбить так, что каждый этап компилируется?
- **Плюсы/минусы**
- **Риски** — что может пойти не так
- **Трудоёмкость** — файлы, строки

### 2.5. Выбор варианта

Критерии для FEAT (отличаются от BUG и DEBT):
- **Корректность физики** — уравнения реализованы правильно
- **Backward compatibility** — при выключенной фиче всё как было
- **Расширяемость** — не закрывает ли путь для следующих фич из roadmap
- **Тестируемость** — каждый аспект проверяем
- **Инкрементальность** — можно реализовать по частям

### 2.6. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Backward compatibility:** при параметре=0 результаты побитово совпадают с текущими
- [ ] **Размерности:** все новые величины в согласованных единицах
- [ ] **Якобиан:** новые производные корректны (проверить аналитически или конечной разностью)
- [ ] **Граничные случаи:** нулевые/экстремальные значения нового параметра
- [ ] **Численная устойчивость:** не появляются ли деление на ноль, overflow, NaN
- [ ] **Потокобезопасность:** если затрагивает OpenMP-секции
- [ ] **Зависимости сборки:** CMakeLists.txt, include paths
- [ ] **Связь с другими задачами:** зависимости и конфликты с BUG/DEBT/FEAT/VAL/RES
- [ ] **Производительность:** не деградирует ли на существующих сценариях
- [ ] **Зависимость от данных:** нужны ли новые входные параметры (PVT, кривые)

### 2.7. Аналитические решения для верификации

Если подтип «Физика», «Режим» или «Модель»:

1. Есть ли аналитическое/полуаналитическое решение для тестовой задачи?
2. Какие упрощения нужны (1D, однородный пласт, одна скважина)?
3. Формулы, ссылки на литературу
4. Допустимая ошибка (tolerance)
5. Есть ли результат MRST/ECLIPSE для сравнения?

### 2.8. Обнаружение новых проблем

Зафиксировать, определить блокирует ли, включить в план или отложить.

## Фаза 3: Детализация плана

### 3.1. Шаблон этапов по подтипу

#### Физика / Режим / Модель:

1. **Подготовка** — ветка, зелёные тесты, baseline
2. **Структуры данных** — новые поля, параметры, значения по умолчанию (backward compat)
3. **Ядро** — реализация уравнений, дискретизация, вклад в Якобиан
4. **Тесты backward compatibility** — при параметре=0 результат побитово совпадает
5. **Тесты нового функционала** — unit-тесты для нового кода
6. **Интеграция** — подключение к `ReservoirSimulator`, `Wells`, `OilField`
7. **Интеграционные тесты** — полноценный сценарий с новой фичей
8. **Верификация vs аналитика** — сравнение с аналитическим решением (если есть)
9. **Визуальная верификация** — CSV export + анимация
10. **Очистка** — обновить vault, закрыть issue

Ключевое правило: **после каждого шага проект компилируется и все тесты зелёные.**

#### Масштабирование:

1. **Подготовка** — ветка, baseline: время, память, профиль
2. **Инструментация** — замеры до оптимизации
3. **Реализация** — по одной оптимизации за шаг
4. **Замеры** — профиль после, сравнение с baseline
5. **Тесты** — результаты идентичны (инвариант) + новый бенчмарк
6. **Очистка**

#### Инфраструктура:

1. **Подготовка** — ветка, понять текущее поведение
2. **Проектирование формата** — схема, примеры
3. **Парсер/генератор** — реализация + unit-тесты
4. **Интеграция** — подключение к основному коду
5. **End-to-end тест** — полный цикл: вход → симуляция → выход
6. **Очистка**

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение

**Файлы:** <полные пути>

**Контекст:**
Для читателя без контекста: что есть сейчас, что хотим,
почему именно так. Физические уравнения, ссылки на vault-заметки.

**Что сделать:**
1. Конкретное действие с файлом, функцией, строкой
2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Сборка: `cmake --build build --config Release`
- Тесты: `ctest --test-dir build -C Release`
- Backward compat: <какой конкретный тест проверяет>
- Все тесты должны остаться зелёными

**Подводные камни:**
- <ссылки на чеклист 2.6>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Тестовая стратегия

Для фичи тесты строятся вокруг:

1. **Backward compatibility:** при параметре=0 результат идентичен текущему (перечислить конкретные тесты)
2. **Unit-тесты нового кода:** каждая новая функция/метод протестирована
3. **Интеграционные тесты:** полноценный сценарий с включённой фичей
4. **Аналитическое сравнение:** если есть аналитическое решение — тест с tolerance (перечислить формулы)
5. **Visual:** CSV + анимация для ключевых сценариев

Формат:
```
**Тест:** <название Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp (существующий / новый)
**Сценарий:** <что проверяем — на уровне физики>
**Setup:** <сетка, начальные условия, параметры фичи>
**Ожидание:** <конкретные числа, неравенства, или качественные свойства>
**Baseline:** <с чем сравниваем — если применимо>
**Backward compat:** <при каком параметре=0 проверяется — если применимо>
**Предотвращает:** <какой класс ошибок этот тест ловит>
```

### 3.4. Критерии завершения

- [ ] Все шаги выполнены
- [ ] Все существующие тесты зелёные (backward compatibility)
- [ ] Новые unit-тесты зелёные
- [ ] Интеграционный тест зелёный
- [ ] Аналитическое сравнение пройдено (если применимо)
- [ ] Визуальная верификация пройдена
- [ ] Фича отключаема (при параметре=0 результат не меняется)
- [ ] Vault обновлён: статус фичи, заметки
- [ ] GitHub issue прокомментирован с результатом, закрывается при merge (если создан)
- [ ] Roadmap фаза обновлена

### 3.5. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Прочитай математическую модель: vault/GDM/atlas/математическая модель двухфазной фильтрации.md
4. Создай ветку: `git checkout -b <branch>`
5. Собери: `cmake -B build -S . -G "Visual Studio 17 2022"; if ($?) { cmake --build build --config Release }`
6. Прогони тесты (baseline): `ctest --test-dir build -C Release`
7. Запомни количество тестов и время — это baseline
8. Начни с шага 1. После каждого шага: сборка + тесты
```

## Фаза 4: Верификация плана (3 раунда)

### Раунд 1: Полнота

- [ ] Каждый затронутый файл упомянут хотя бы в одном шаге
- [ ] Для каждого шага есть проверка
- [ ] Зависимости шагов — без циклов
- [ ] Все подводные камни (2.6) адресованы
- [ ] Критерии завершения проверяемы
- [ ] Backward compatibility проверяется явным тестом
- [ ] Физическое обоснование полное (уравнения, размерности, предельные случаи)
- [ ] После каждого шага проект компилируется и тесты зелёные

### Раунд 2: Корректность

Общее (для каждого шага):
- [ ] Упомянутые методы/поля/типы существуют (grep)
- [ ] Типы совместимы
- [ ] Номера строк актуальны

Специфичное для фичи:
- [ ] Уравнения корректны (дискретизация, производные, знаки)
- [ ] Размерности согласованы
- [ ] CMake-изменения корректны (если добавляются новые файлы/цели)

### Раунд 3: Автономность

Представь: Claude в новой сессии с compact-контекстом.

- [ ] Каждый шаг самодостаточен
- [ ] Полные пути к файлам
- [ ] Объяснено ПОЧЕМУ, а не только ЧТО
- [ ] Физический/математический контекст: уравнения, ссылки на vault, литература
- [ ] Термины расшифрованы
- [ ] «Как начать работу» — конкретные команды
- [ ] Baseline зафиксирован (количество тестов, время)

Проблемы → исправить → повторить раунд.

Путь: `vault/GDM/plans/<id-lowercase> <slug>.md`

Frontmatter:
```yaml

tags:
  - план

  - <подтип: физика | режим | модель | масштабирование | инфраструктура>
```

1. В записи фичи (`планируемые фичи.md`): `- **План:** [[<имя плана>]]`
2. Если есть GitHub issue: `gh issue comment <N> --repo ArturSalamatin/GDM --body "План: vault/GDM/plans/<файл>. Ветка: <branch>. Шагов: <N>."`
3. В `vault/GDM/00-home/index.md` — секция Plans

### 5.3. Зафиксировать новые проблемы

Из фазы 2.8 → соответствующий реестр с новыми ID.

### 5.4. Сообщить результат

- Путь к плану
- Подтип фичи
- Фаза roadmap
- Этапов / шагов
- Новые проблемы (если есть)
- Ветка
- Оценка: файлов, строк, время

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Избыточность лучше недосказанности — особенно в физическом обосновании
- Инкрементальность: после каждого шага проект компилируется и тесты зелёные
- Backward compatibility — обязательный инвариант, не опциональный
- Если >15 шагов — разбить на под-задачи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
