# /plan-validate — план валидационного кейса

Аргумент: `$ARGUMENTS` — идентификатор кейса (например `VAL-001`, `VAL-003`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

---

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/GDM/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/GDM` → из title извлеки ID (формат: `VAL-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/GDM/roadmap/валидационные кейсы.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM`
3. Прочитай подробную заметку из `knowledge/validation/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Определить подтип

| Подтип | Признак | Пример |
|---|---|---|
| **Аналитический** | есть точное/полуаналитическое решение | VAL-001: Buckley–Leverett |
| **Сетчатая сходимость** | серия сеток, порядок сходимости | VAL-002: h-refinement |
| **Межсимуляторный** | сравнение с MRST/ECLIPSE/tNavigator | VAL-003: five-spot vs MRST |
| **Инвариантный** | проверка закона сохранения, симметрии | VAL-006: баланс масс |

### 1.4. Извлечь имя ветки

1. Из GitHub issue или vault-записи
2. Если нет — сгенерируй: `val/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.5. Загрузить связанные заметки

1. Wiki-ссылки из записи — прочитать каждую
2. `vault/GDM/atlas/математическая модель двухфазной фильтрации.md` — текущая мат. модель
3. `vault/GDM/knowledge/physics/` — физические заметки по теме кейса
4. `vault/GDM/knowledge/validation/` — существующие результаты валидации
5. `vault/GDM/roadmap/стратегия тестирования GDM.md` — паттерны тестов
6. `vault/GDM/roadmap/инвентаризация кодовой базы*.md` — какие модули затронуты
7. Зависимости: есть ли блокирующие BUG/DEBT/FEAT/RES?

### 1.6. Исследовать код

1. **Существующие тесты:** grep в `tests/` по ключевым словам кейса (buckley, five-spot, balance)
2. **Существующие examples:** grep в standalone examples — может быть готовый сценарий
3. **CSV export:** как настроен вывод результатов, формат, snapshot_dt
4. **Python-скрипты:** есть ли визуализация для этого типа задач
5. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности» — существующие тесты, примеры, API ядра, которые валидация не должна затрагивать

## Фаза 2: Проектирование кейса

### 2.1. Эталонное решение

В зависимости от подтипа:

**Аналитический:**
1. Выписать формулы эталонного решения с выводом
2. Упрощения: какие допущения (1D, однородный, без капиллярки, без гравитации)
3. Ссылки на литературу (Buckley & Leverett 1942, Aziz & Settari, Chen et al.)
4. Реализация: как вычислить эталон — формула, код Python, таблица

**Сетчатая сходимость:**
1. Серия сеток (минимум 4 уровня: h, h/2, h/4, h/8)
2. Норма ошибки (L1, L2, L∞)
3. Ожидаемый порядок сходимости (теоретический)
4. Как считать порядок: log(e_h/e_{h/2}) / log(2)

**Межсимуляторный:**
1. Описание сценария в терминах эталонного симулятора (MRST script, ECLIPSE DATA)
2. Какие результаты извлекать (давление, Sw, дебиты, время прорыва)
3. Формат сравнения (pointwise, integral, visual)
4. Допустимая ошибка

**Инвариантный:**
1. Формулировка инварианта (закон сохранения, симметрия)
2. Как измерить невязку
3. Tolerance

### 2.2. Сценарий GDM

1. **Сетка:** размеры, число ячеек, тип
2. **Физика:** PVT параметры, rel perm, начальные условия
3. **Скважины:** тип, расположение, режим, расписание
4. **Время:** шаг, число шагов, snapshot_dt
5. **Параметры солвера:** Newton tolerance, максимум итераций
6. **Код:** какой example/тест использовать как основу, что модифицировать

### 2.3. Метрики сравнения

Для каждой метрики:
- Что сравниваем (поле давления, профиль Sw, кривая добычи)
- Как считаем ошибку (L2-норма, относительная, абсолютная)
- Tolerance (при каком значении считаем «прошло»)
- Визуализация (overlay plot, difference map, convergence curve)

### 2.4. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Блокирующие баги:** BUG-NNN, которые делают прогон невозможным
- [ ] **Согласованность единиц:** [[таблица единиц GDM vs MRST]]
- [ ] **Граничные условия:** тип BC в GDM совпадает с эталоном
- [ ] **Начальные условия:** Sw_init, P_init — совпадают с эталоном
- [ ] **Временной шаг:** достаточно мал для точности, достаточно велик для скорости
- [ ] **Сетка:** ориентация, нумерация — совпадают с эталоном
- [ ] **Численная диффузия:** upstream-схема размывает фронт — это ожидаемо, не баг
- [ ] **Симметрия:** если кейс симметричен — нарушение симметрии = баг

### 2.5. Обнаружение новых проблем

Зафиксировать, определить блокирует ли, включить в план или отложить.

## Фаза 3: Детализация плана

### 3.1. Этапы валидации

1. **Подготовка** — ветка, зелёные тесты, baseline
2. **Эталон** — реализовать/импортировать эталонное решение (Python-скрипт или таблица)
3. **Сценарий GDM** — создать/адаптировать тест в Catch2
4. **Прогон** — запустить, убедиться что не падает
5. **Сбор результатов** — CSV export, snapshot-ы
6. **Сравнение** — вычислить метрики, построить графики
7. **Тесты** — Catch2 assert на метрики (L2 < tolerance)
8. **Визуальная верификация** — overlay plots, анимация
9. **Документация** — обновить vault: заметка в `knowledge/validation/`, статус в реестре
10. **Очистка** — прокомментировать issue

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение

**Файлы:** <полные пути>

**Контекст:**
Для читателя без контекста: физика кейса, что сравниваем,
какой результат ожидаем. Ссылки на vault-заметки.

**Что сделать:**
1. Конкретное действие
2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Сборка: `cmake --build build --config Release`
- Тесты: `ctest --test-dir build -C Release`
- Все существующие тесты зелёные

**Подводные камни:**
- <ссылки на чеклист 2.4>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Тестовая стратегия

Для валидации тесты строятся вокруг:

1. **Количественный тест:** Catch2 assert на метрику (L2 < tolerance, error < 1%, порядок > 0.9)
2. **Regression:** существующие тесты не ломаются
3. **Visual:** overlay plot (GDM vs эталон), difference map, convergence curve
4. **Инвариантный:** баланс масс, симметрия (если применимо)

Формат:
```
**Тест:** <название Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp (существующий / новый)
**Сценарий:** <что проверяем — на уровне физики>
**Setup:** <сетка, начальные условия, параметры>
**Эталон:** <аналитика / MRST / fine-grid>
**Метрика:** <L2, L∞, relative error>
**Tolerance:** <конкретное число>
**Предотвращает:** <какой класс ошибок ловит>
```

### 3.4. Критерии завершения

- [ ] Все шаги выполнены
- [ ] Все существующие тесты зелёные
- [ ] Новый количественный тест зелёный (метрика < tolerance)
- [ ] Визуальная верификация пройдена (графики в vault)
- [ ] Баланс масс проверен (если применимо)
- [ ] Vault обновлён: заметка в `knowledge/validation/`, статус в реестре
- [ ] GitHub issue прокомментирован с результатом, закрывается при merge (если создан)
- [ ] Roadmap фаза обновлена (если кейс входит в фазу)

### 3.5. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Прочитай математическую модель: vault/GDM/atlas/математическая модель двухфазной фильтрации.md
4. Создай ветку: `git checkout -b <branch>`
5. Собери: `cmake -B build -S . -G "Visual Studio 17 2022"; if ($?) { cmake --build build --config Release }`
6. Прогони тесты (baseline): `ctest --test-dir build -C Release`
7. Запомни количество тестов и время — это baseline
8. Начни с шага 1. После каждого шага: сборка + тесты
```

## Фаза 4: Верификация плана (3 раунда)

### Раунд 1: Полнота

- [ ] Эталонное решение полностью описано (формулы, код, или ссылка на результаты)
- [ ] Сценарий GDM полностью параметризован
- [ ] Метрики определены с tolerance
- [ ] Все подводные камни (2.4) адресованы
- [ ] Визуализация запланирована
- [ ] После каждого шага проект компилируется и тесты зелёные

### Раунд 2: Корректность

Общее (для каждого шага):
- [ ] Упомянутые методы/поля/типы существуют (grep)
- [ ] Типы совместимы
- [ ] Номера строк актуальны

Специфичное для валидации:
- [ ] Формулы эталона корректны (проверить по литературе)
- [ ] Единицы согласованы (GDM vs эталон)
- [ ] Tolerance обоснован (не слишком жёсткий и не слишком мягкий)

### Раунд 3: Автономность

Представь: Claude в новой сессии с compact-контекстом.

- [ ] Каждый шаг самодостаточен
- [ ] Полные пути к файлам
- [ ] Объяснено ПОЧЕМУ, а не только ЧТО
- [ ] Физический контекст: уравнения эталона, ссылки на vault и литературу
- [ ] Термины расшифрованы
- [ ] «Как начать работу» — конкретные команды
- [ ] Baseline зафиксирован (количество тестов, время)

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Ключевое: эталон должен быть полностью описан (формулы, параметры, код) — без этого план бесполезен
- Визуальная верификация обязательна — не только Catch2 assert
- Если >15 шагов — разбить на под-задачи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
