# /implement — реализация плана из vault

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `BUG-001`, `FEAT-003`) или путь к файлу плана (например `vault/GDM/plans/bug-001 well-state-rollback.md`).

Результат: задача реализована, код скомпилирован, тесты проходят, vault обновлён, коммиты созданы.

**Ключевой принцип:** делать ТОЛЬКО то, что написано в плане. Не рефакторить «по дороге», не добавлять «раз уже тут», не оптимизировать то, что не в скоупе.

---

## Фаза 1: Подготовка

### 1.1. Найти план

Если `$ARGUMENTS` — ID задачи:
```
ls vault/GDM/plans/<id-lowercase>*
```
Если `$ARGUMENTS` — путь к файлу: использовать напрямую.

Если план не найден — сообщи пользователю и предложи сначала создать:
- BUG → `/plan-fix <ID>`
- DEBT → `/plan-improve <ID>`
- FEAT → `/plan-feature <ID>`
- VAL → `/plan-validate <ID>`
- RES → `/plan-research <ID>`

### 1.2. Загрузить план

1. Прочитай файл плана целиком
2. Извлеки из frontmatter: `issue`, `github`, `branch`, `status`
3. Если `status` ≠ `готов к реализации` — сообщи пользователю (может быть `в процессе`, `реализован`, `отменён`)

### 1.3. Загрузить контекст

Следуй секции «Как начать работу по этому плану» из файла плана:
1. Прочитай связанные vault-заметки (ссылки в плане)
2. Если есть GitHub issue — прочитай: `gh issue view <N> --repo ArturSalamatin/GDM` (там могут быть комментарии с уточнениями)

### 1.4. Подготовить ветку

1. Извлеки имя ветки из frontmatter плана (`branch:`)
2. Проверь текущую ветку: `git branch --show-current`
3. Проверь чистоту: `git status`
   - Если есть незакоммиченные изменения — **СТОП**, сообщи пользователю
4. Проверь существование ветки: `git branch --list "<branch>"`
   - Ветка существует → `git checkout <branch>`
   - Ветки нет → `git checkout -b <branch>`
5. Обнови frontmatter плана: `status: в процессе`

### 1.5. Зафиксировать baseline

```powershell
cmake -B build -S . -G "Visual Studio 17 2022"
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Запомни:
- Количество тестов
- Количество passed / failed / skipped
- Время выполнения
- Если есть failing тесты — это известные проблемы или новые? Проверь по `[.]` тегам и vault

## Фаза 2: Реализация

### 2.1. Порядок выполнения

Выполняй шаги плана **строго последовательно**. Для каждого шага:

1. **Перечитай шаг** — цель, файлы, контекст, что сделать, подводные камни
2. **Проверь актуальность** — grep упомянутые методы/поля, убедись что номера строк не съехали
3. **Реализуй** — минимально необходимые изменения
4. **Собери** — `cmake --build build --config Release`
   - Если не компилируется — исправь немедленно, до любых других действий
5. **Прогони тесты** — `ctest --test-dir build -C Release --output-on-failure`
6. **Проверь результат шага** — выполни «Проверка после этого шага» из плана
7. **Коммит** — если шаг завершён и всё зелёное (см. 2.2)

### 2.2. Стратегия коммитов

Каждый коммит — самодостаточный блок. Критерии:

- [ ] Код компилируется (`cmake --build build --config Release` — без ошибок)
- [ ] Все таргеты собираются (основной + тесты + examples)
- [ ] Все тесты проходят (или failing тесты явно задокументированы — см. 2.4)
- [ ] Изменения логически связаны (один шаг плана = один или несколько коммитов)

Формат сообщения: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`
- Vault-изменения — **отдельным коммитом** от кода (`vault: ...`)
- Stage по имени файла, **не** `git add .` или `git add -A`
- **Не** упоминай Claude в коммитах (без Co-Authored-By)

Когда коммитить:
- После каждого завершённого шага плана (если шаг затрагивает код)
- После группы мелких связанных шагов (если каждый по отдельности не имеет смысла)
- **Перед** переходом к шагу, который затрагивает другую подсистему
- При обновлении vault — отдельный коммит

### 2.3. Обнаружение новых проблем

В ходе реализации могут всплыть неожиданные проблемы. Протокол:

1. **Не уходи в сторону.** Не начинай чинить найденную проблему, если она не в плане
2. **Зафиксируй** — добавь в `vault/GDM/inbox/` короткую заметку:
   ```
   ---
   tags: [inbox, обнаружено-при-реализации]
   date: <дата>
   source: <ID текущей задачи>
   ---
   # <суть проблемы>
   Обнаружено при реализации [[<план>]].
   <описание: что увидел, почему это проблема>
   ```
3. **Оцени блокирует ли** — мешает ли эта проблема завершить текущий шаг?
   - Не блокирует → продолжай план
   - Блокирует → СТОП, сообщи пользователю, предложи варианты:
     a) Обходной путь в рамках плана
     b) Приостановить, создать `/issue` для блокера, вернуться после

### 2.4. Что делать если тесты не проходят

После выполнения шага тесты могут упасть. Алгоритм:

1. **Тест упал из-за текущих изменений** (новый тест или сломан существующий):
   - Исправь в рамках текущего шага
   - Если не удаётся за разумное время (~15 минут) → п.3

2. **Тест упал по не связанной причине** (flaky, известный баг):
   - Проверь — есть ли это в vault (`knowledge/debugging/`, реестр багов)
   - Если известный — продолжай, укажи в коммите: `fix: <описание> (тест X flaky, см. BUG-NNN)`

3. **Не удаётся починить:**
   - `git stash` текущие изменения
   - Зафиксируй в vault как новый BUG/DEBT
   - Сообщи пользователю: что сломалось, почему, какие варианты
   - **Не коммить сломанное состояние**

### 2.5. Прогресс

После каждого шага кратко сообщи:
```
Шаг N/M: <название> ✅
  Файлы: <список>
  Тесты: <passed>/<total> (baseline: <baseline>)
  Коммит: <hash> <message>
```

Если шаг занимает много изменений — сообщай промежуточный статус.

## Фаза 3: Верификация

После выполнения всех шагов плана.

### 3.1. Чеклист критериев завершения

Пройди чеклист «Критерии завершения» из плана. Для каждого пункта — подтверди или укажи проблему.

### 3.2. Финальная сборка и тесты

```powershell
cmake --build build --config Release 2>&1 | Select-Object -Last 5
ctest --test-dir build -C Release --output-on-failure
```

Сравни с baseline:
- Количество тестов: было → стало
- Время: было → стало
- Новые тесты: какие добавлены

### 3.3. Визуальная верификация

Если план предусматривает визуальную верификацию (CSV + анимация/графики):
1. Убедись что CSV-файлы генерируются
2. Убедись что Python-скрипты отрабатывают
3. Результаты — в vault или build/

### 3.4. Обзор изменений

```powershell
git log --oneline <base-branch>..HEAD
git diff --stat <base-branch>..HEAD
```

Проверь:
- [ ] Нет случайных файлов (build артефакты, логи, .vs/)
- [ ] Нет отладочного кода (printf, std::cout, #if 0)
- [ ] Нет закомментированного старого кода
- [ ] Vault-изменения в отдельных коммитах от кода

## Фаза 4: Финализация

### 4.1. Обновить vault

1. **Реестр** — обновить статус задачи:
   - BUG/DEBT → `известные баги и технический долг.md`: `**Статус:** ✅ исправлено <дата>`
   - FEAT → `планируемые фичи.md`: `**Статус:** ✅ реализовано <дата>`
   - VAL → `валидационные кейсы.md`: `**Статус:** ✅ пройден <дата>`
   - RES → `исследования и эксперименты.md`: `**Статус:** ✅ завершён <дата>` или `❌ отвергнуто <дата>`

2. **План** — обновить frontmatter: `status: реализован`

3. **Knowledge** (если применимо):
   - Исправлен баг → заметка в `knowledge/debugging/` (симптом, причина, фикс)
   - Принято решение → заметка в `knowledge/decisions/`
   - Результат валидации → обновить `knowledge/validation/`
   - Результат эксперимента → заметка с выводом, графиками

4. **Приоритеты** — обновить `vault/GDM/00-home/текущие приоритеты.md` если задача была в приоритетах

5. **Index** — обновить `vault/GDM/00-home/index.md` если созданы новые заметки

6. **Коммит vault-изменений** — отдельно: `vault: результаты <ID> <краткое описание>`

### 4.2. Закрыть GitHub issue

Если есть GitHub issue (поле `github` в frontmatter плана):

```powershell
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")
gh issue close <N> --repo ArturSalamatin/GDM --comment "<комментарий>"
```

Комментарий зависит от типа:
- BUG: `Исправлено в ветке <branch>. Причина: <причина>. Тесты: <N> passed.`
- DEBT: `Реализовано в ветке <branch>. Тесты: <N> passed.`
- FEAT: `Реализовано в ветке <branch>. Новые тесты: <список>. Всего тестов: <N>.`
- VAL: `Пройден. Метрика: <значение> < <tolerance>. Результаты: vault/GDM/knowledge/validation/<файл>.`
- RES: `Завершён. Вывод: <гипотеза подтверждена/отвергнута>. Результаты: vault/GDM/knowledge/<файл>.`

### 4.3. Обработать inbox

Если в ходе реализации были найдены новые проблемы (заметки в `vault/GDM/inbox/`):
1. Для каждой заметки: определи тип (BUG/DEBT/FEAT/VAL/RES)
2. Добавь в соответствующий реестр с новым ID
3. Удали из inbox
4. Сообщи пользователю: «Обнаружено N новых проблем: <список>»

### 4.4. Сообщить результат

```
## Результат /implement <ID>

**Статус:** ✅ реализовано / ⚠️ частично / ❌ заблокировано

**Ветка:** <branch>
**Коммиты:** <N> (<список хешей>)
**Тесты:** <baseline> → <итог> (+<новых>)

**Что сделано:**
- <пункт 1>
- <пункт 2>

**Vault обновлён:**
- <список файлов>

**Новые проблемы:** <список или «нет»>

**Следующий шаг:** <рекомендация>
```

## Протокол отката

Если реализация зашла в тупик (сборка сломана и не чинится, тесты массово падают, блокирующая проблема):

1. **Не коммить сломанное состояние**
2. `git stash` — сохрани текущие изменения
3. Обнови frontmatter плана: `status: заблокирован`, добавь `blocker: <описание>`
4. Зафиксируй блокер в vault (inbox или реестр)
5. Сообщи пользователю: что пошло не так, на каком шаге, какие варианты
6. Vault-коммит с обновлённым статусом: `vault: <ID> заблокирован — <причина>`

## Примечания

- Язык: русский
- Делать ТОЛЬКО то, что в плане. Улучшения «по дороге» → inbox, не в код
- Коммиты частые и самодостаточные. Каждый компилируется и тесты зелёные
- Vault-изменения отдельным коммитом от кода
- Stage по имени файла, не `git add .`
- Не упоминай Claude в коммитах
- При ошибке сборки — исправляй и пересобирай автоматически, без запроса подтверждения
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
