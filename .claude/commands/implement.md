# /implement — реализация плана из vault

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `BUG-001`, `FEAT-003`) или путь к файлу плана (например `vault/GDM/plans/bug-001 well-state-rollback.md`).

Результат: задача реализована на ветке задачи в отдельном worktree – код скомпилирован (Release + Debug, без warnings), тесты проходят, запись в журнале изменений `CHANGELOG.md`, vault обновлён, комментарий к GitHub issue, коммиты созданы. Влитие в `experimental` – отдельной командой `/merge <ID>` по слову пользователя «мерж».

**Ключевой принцип:** делать ТОЛЬКО то, что написано в плане. Не рефакторить «по дороге», не добавлять «раз уже тут», не оптимизировать то, что не в скоупе.

## Схема работы

Задача выполняется в отдельном worktree. Основной каталог проекта стоит на базовой ветке `experimental`, его рабочую копию делят параллельные сессии.

| Что | Где правится | Куда коммитится |
|---|---|---|
| Подготовленное **до** реализации: план, материалы задачи (`vault/GDM/issues/<id>/` – тексты issue, пробы аудита), общие файлы vault (реестры, `index.md`) | основной каталог | `experimental` – предварительный коммит (1.4), до создания worktree |
| Код, тесты, журнал изменений `CHANGELOG.md` (4.1); vault, изменённый **во время** реализации (статус плана, запись задачи в реестре, заметки результатов, `05-comment-done.md`) | worktree | ветка задачи |
| Новые задачи, обнаруженные при реализации (2.3) | основной каталог | `experimental`, сразу |
| Влитие, удаление worktree, отметка «влит» | основной каталог | `experimental` – `/merge` |

Обозначения (в командах подставлять полностью):

- `<КОРЕНЬ>` = `d:\Lessons\Grants\2027\GDM` – основной каталог.
- `<W>` = `<КОРЕНЬ>\.worktrees\<id-lowercase>` – worktree задачи (например `.worktrees\bug-024`).
- `<W>\build` – своя сборка worktree. Сборка и тесты – только в ней: `build\` основного каталога собран из кода `experimental`, а не ветки задачи.

Переменные PowerShell (`$x = ...`) не переживают отдельный вызов инструмента – задавать в той же команде, что и использование.

Уровни прогона тестов (тесты строго последовательно, без `-j`):
```
ctest --test-dir <W>\build -C Release -R "^unit\." --output-on-failure   # быстрый уровень (unit.level0–4) – на каждом шаге
ctest --test-dir <W>\build -C Release --output-on-failure                # полный прогон (+ integration., benchmark.) – на шагах «Регресс: полный» и в конце
ctest --test-dir <W>\build -C Release -N                                 # число тестов без прогона
```

### Правила работы в worktree

1. **Код правится только в `<W>`.** Read / Edit / Write – по абсолютному пути `<W>\...`. Относительные пути в обоих деревьях одинаковы: тот же путь от `<КОРЕНЬ>` молча изменит основной каталог, а не ветку задачи. В основном каталоге – только то, что «Схема работы» относит к `experimental`.
2. **Контроль основного каталога.** На шаге 1.7 запомни `git -C <КОРЕНЬ> status --porcelain -- src/ HydroSolver/ tests/ examples/ CMakeLists.txt`; после каждого шага сверяй. Новая строка – проверь, не своя ли это ошибочная правка: своя → перенести в `<W>`, в основном каталоге вернуть текст Edit-ом; чужая (параллельная сессия) – не трогать.
3. **Подмодуль `amgcl`.** `git worktree add` оставляет каталоги подмодулей пустыми, а сборка берёт `amgcl` из `${CMAKE_SOURCE_DIR}/amgcl` (`CMakeLists.txt`). В worktree инициализируется только `amgcl` (1.5): `Eigen` код GDM не подключает, `GridEngine` лежит за VPN (`10.8.0.1`) и сборке не нужен. Подмодуль не правится.
4. **Пробы** `vault/GDM/issues/<id>/probes/` лежат в git с предварительного коммита (1.4) и есть в worktree. Запускать копию из `<W>`, исполняемые файлы – из `<W>\build`. Новые пробы – в `<W>\vault\GDM\issues\<id>\probes\`, коммит на ветке задачи (`vault:`).
5. **git задачи** – в `<W>` (`git -C <W> ...`). Коммиты кода и vault задачи – на ветке задачи.
6. **Коммит в `experimental`** (1.4, 2.3, 4.4) – в `<КОРЕНЬ>`, с явными путями:
   ```powershell
   git -C <КОРЕНЬ> add -- <файлы>
   git -C <КОРЕНЬ> commit -m "<сообщение>" -- <файлы>
   ```
   Коммит с путями берёт только их и не захватывает то, что параллельная сессия уже добавила в индекс.
7. **`git stash` не использовать.** Список stash общий для всех worktree репозитория: спрятанное в worktree видно и применимо в основном каталоге и в чужих worktree. Незакоммиченное состояние worktree и так изолировано – его оставляют на месте.
8. **Встроенные `EnterWorktree` / `ExitWorktree` не использовать.** `EnterWorktree` создаёт worktree в `.claude/worktrees/` и ветвится от ветки по умолчанию `origin` (`dev`), `ExitWorktree remove` удаляет ветку. Worktree создаётся вручную (1.5).
9. **Игнорируемые git файлы worktree удаляются вместе с ним** (`<W>\build`, `<W>\results`). Всё, что нужно сохранить, – в отслеживаемых файлах, закоммичено на ветке. Результаты расчётов, на которые ссылаются план, реестр или заметки, перед `/merge` скопировать в `<КОРЕНЬ>\results\`: `/merge` проверяет это до удаления worktree.

## Фаза 1: Подготовка

Шаги 1.1–1.4 – в основном каталоге `<КОРЕНЬ>`.

### 1.1. Найти план

Если `$ARGUMENTS` — ID задачи:
```
ls vault/GDM/plans/<id-lowercase>*
```
(в основном каталоге: план может быть ещё не закоммичен). Если `$ARGUMENTS` — путь к файлу: использовать напрямую.

Если worktree задачи уже есть (`git worktree list`) – актуальный план в `<W>\vault\GDM\plans\` (возобновление, 2.6).

Если план не найден — сообщи пользователю и предложи сначала создать:
- BUG → `/plan-fix <ID>`
- DEBT → `/plan-improve <ID>`
- FEAT → `/plan-feature <ID>`
- VAL → `/plan-validate <ID>`
- RES → `/plan-research <ID>`

### 1.2. Загрузить план

1. Прочитай файл плана целиком
2. Извлеки из frontmatter: `issue`, `github`, `branch`, `status`, `worktree`
3. Проверь `status`:
   - `готов к реализации` → продолжай с шага 1.3
   - `в процессе` → возобновление, перейди к 2.6
   - `черновик` → предложи `/audit-plan`
   - `реализован` → предложи `/merge <ID>`
   - `отменён` / `заблокирован` → сообщи пользователю, не продолжай без подтверждения

Пункт «Создай ветку» (`git checkout -b`) из секции плана «Как начать работу» в старых планах **не выполнять**: ветку и worktree создаёт шаг 1.5. `git checkout -b` в основном каталоге увёл бы в ветку задачи коммиты параллельных сессий.

### 1.3. Проверить предусловия и синхронизировать experimental с main

1. **Блокирующие задачи завершены и влиты.** Для каждой задачи из «Зависит от» и блокеров из реестра: запись в реестре – «влит», ветка – предок базы: `git merge-base --is-ancestor <ветка зависимости> experimental` (код возврата 0). Хоть одна не влита – **СТОП**: задача не выполняется, пока блокирующие задачи не завершены и не влиты. Ветвиться от ветки невлитой задачи нельзя.
2. **Основной каталог стоит на `experimental`:** `git -C <КОРЕНЬ> branch --show-current`. Иначе – СТОП: предварительный коммит ушёл бы не в ту ветку.
3. **Ветки задачи и worktree нет:** `git branch --list "<branch>"`, `git worktree list`. Ветка есть при статусе `готов к реализации` – СТОП, вопрос пользователю (прежняя попытка? чужая работа?).
4. **`.worktrees/` исключён из git:** в `.git/info/exclude` есть строка `/.worktrees/` (`Select-String -Path <КОРЕНЬ>\.git\info\exclude -Pattern '^/?\.worktrees/?$'`). Нет – добавить.
5. **experimental содержит все изменения из main:**
   ```powershell
   git -C <КОРЕНЬ> merge main
   ```
   - Если merge прошёл без конфликтов (или «Already up to date») — продолжай
   - Если конфликты — **СТОП**, сообщи пользователю: «Конфликт при merge main → experimental. Разреши конфликты, закоммить merge и перезапусти `/implement`.» Не пытайся разрешать конфликты самостоятельно

### 1.4. Предварительный коммит в experimental

План и материалы, подготовленные до реализации, – часть базовой ветки, и в worktree они должны быть: worktree создаётся от `experimental` после этого коммита.

1. `git -C <КОРЕНЬ> status --porcelain` – изменения основного каталога.
2. Разбери по группам:

| Группа | Что | Действие |
|---|---|---|
| Материалы задачи | план `vault/GDM/plans/<id>*`; `vault/GDM/issues/<id>/` (тексты issue, пробы); заметки vault, которые называет план | в коммит |
| Общие файлы vault | реестры `vault/GDM/roadmap/*.md`, `vault/GDM/00-home/index.md`, `vault/GDM/00-home/текущие приоритеты.md` – регистрация и краткие описания задач | в коммит **целиком**, даже если в файле правки других задач: им и так место в базовой ветке |
| Код задачи | незакоммиченные правки `src/`, `HydroSolver/`, `tests/`, `examples/`, `CMakeLists.txt`, относящиеся к задаче | **СТОП**, вопрос пользователю: в базу без зелёных тестов нельзя, а незакоммиченное в worktree не попадёт |
| Прочее | планы и материалы других задач, чужие правки кода | не трогать |

3. Обнови frontmatter плана: `status: в процессе`, `worktree: .worktrees/<id-lowercase>`.
4. Коммит – правило 6: `vault: <ID> начало реализации – план и материалы задачи`.
5. Сообщи в чат: что вошло в коммит (по группам), что оставлено, hash.

### 1.5. Создать worktree

Базовая ветка – `experimental` (CLAUDE.md, «Коммиты»). Если план указывает другую – СТОП, вопрос пользователю.

```powershell
git -C <КОРЕНЬ> worktree add .worktrees/<id-lowercase> -b <branch-from-plan> experimental
git -C <W> submodule update --init --reference <КОРЕНЬ>\.git\modules\amgcl amgcl
```

`--reference` берёт объекты подмодуля из основного каталога, без сети; если git отказал – повтори без `--reference` (клон с GitHub).

Сборка в worktree – с нуля (Catch2 берётся из уже скачанного в основном каталоге, без сети):
```powershell
cmake -S <W> -B <W>\build -G "Visual Studio 17 2022" -DFETCHCONTENT_SOURCE_DIR_CATCH2=<КОРЕНЬ>\build\_deps\catch2-src
```

Проверка: `git -C <W> log --oneline -1` – предварительный коммит из 1.4; план в `<W>\vault\GDM\plans\` со статусом `в процессе`; `git -C <W> status --porcelain` пуст; `<W>\amgcl\` не пуст.

### 1.6. Загрузить контекст (из worktree)

Следуй секции «Как начать работу по этому плану» из файла плана (кроме создания ветки – см. 1.2):
1. Прочитай связанные vault-заметки (`<W>\vault\GDM\...`)
2. Прочитай файлы, которые будут изменены (`<W>\...`, только нужные фрагменты)
3. Если есть GitHub issue — прочитай: `gh issue view <N> --repo ArturSalamatin/GDM` (там могут быть комментарии с уточнениями от аудита или пользователя)

### 1.7. Зафиксировать baseline (в worktree)

Baseline фиксируется **для обоих конфигов — Release и Debug**. Оба конфига обязательны: Debug ловит UB, неинициализированную память и assert'ы, которые Release пропускает.

**Важно — последовательность:**
- Тесты — **строго последовательно**: не использовать `ctest -j`, `--parallel`, `CTEST_PARALLEL_LEVEL`. Причина: тесты разделяют ресурсы (файлы, состояние симулятора), параллельный запуск даёт ложные падения
- Release и Debug — **строго последовательно**: сначала полный цикл Release (сборка + тесты), потом полный цикл Debug. Не запускать сборку Debug пока тесты Release не завершились
- **Не запускать ctest в фоне** — дождаться завершения перед следующей командой

```powershell
cmake --build <W>\build --config Release
ctest --test-dir <W>\build -C Release --output-on-failure
cmake --build <W>\build --config Debug
ctest --test-dir <W>\build -C Debug --output-on-failure
```

Сборка worktree идёт с нуля – это дольше обычной инкрементальной; время сборки отметь в отчёте.

Запомни **для каждого конфига (Release + Debug)**:
- Количество тестов
- Количество passed / failed / skipped
- Время выполнения
- Количество warnings в выводе сборки
- Если есть failing тесты — это известные проблемы или новые? Проверь по `[.]` тегам и vault

Отдельно запомни время быстрого уровня (`ctest --test-dir <W>\build -C Release -R "^unit\." --output-on-failure`) – с ним сверяется регрессия после шагов.

Если тесты на базе красные – СТОП: это не регрессия задачи, сообщи пользователю. Если план указывает baseline и он **не совпал** с фактическим – не игнорируй: план мог устареть, сверь и зафиксируй факт.

Также зафиксируй точку ветвления: `git -C <W> merge-base HEAD experimental` – для `git diff` и `git log` в фазе 3. И снимок основного каталога для правила 2: `git -C <КОРЕНЬ> status --porcelain -- src/ HydroSolver/ tests/ examples/ CMakeLists.txt`.

## Фаза 2: Реализация

### 2.1. Порядок выполнения

Все правки – в `<W>`, кроме регистрации новых задач (2.3).

Выполняй шаги плана **строго последовательно**. Для каждого шага:

1. **Перечитай шаг** — цель, файлы, контекст, что сделать, подводные камни
2. **Проверь актуальность** — grep упомянутые методы/поля (в `<W>`), убедись что номера строк не съехали. Если код существенно изменился с момента написания плана (метод удалён, API изменился) — адаптируй шаг в рамках его цели, зафиксируй расхождение в сообщении коммита
3. **Реализуй** — минимально необходимые изменения (абсолютные пути `<W>\...`, правило 1)
4. **Собери** — `cmake --build <W>\build --config Release` (параллельная сборка таргетов допускается)
   - Если не компилируется — исправь немедленно, до любых других действий
   - **Warnings = ошибки.** Проверь вывод на наличие warning. Если есть — исправь по существу (причину, не симптом). Не подавлять через `#pragma warning(disable:...)`, `(void)var`, `-Wno-*` и т.п. Если warning невозможно устранить по существу (например, из внешней библиотеки) — сообщи пользователю с объяснением почему
5. **Прогони тесты** (строго последовательно, без `-j` / `--parallel`):
   - тест шага: `ctest --test-dir <W>\build -C Release -R "<name>" --output-on-failure`
   - регресс по полю «Регресс» шага в плане:
     - `быстрый` (по умолчанию, и если поля нет): `ctest --test-dir <W>\build -C Release -R "^unit\." --output-on-failure`
     - `полный`: `ctest --test-dir <W>\build -C Release --output-on-failure`
     - шаг меняет только документы (vault, `.md`), не код и не тесты: `ctest --test-dir <W>\build -C Release -N` – число тестов не изменилось
   - Debug между шагами не обязателен (экономия времени). Debug — на финальной верификации (фаза 3.2)
6. **Проверь результат шага** — выполни «Проверка после этого шага» из плана
7. **Сверь основной каталог** со снимком из 1.7 (правило 2)
8. **Коммит** — если шаг завершён и всё зелёное (см. 2.2)

### 2.2. Стратегия коммитов

Коммиты – в `<W>` (`git -C <W> ...`), на ветке задачи. Каждый коммит — самодостаточный блок. Критерии:

- [ ] Код компилируется без ошибок **и без warnings** (оба конфига на финальной верификации)
- [ ] Все таргеты собираются (основной + тесты + examples)
- [ ] Все тесты проходят (или failing тесты явно задокументированы — см. 2.4)
- [ ] Изменения логически связаны (один шаг плана = один или несколько коммитов)

Формат сообщения: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`
- Vault-изменения — **отдельным коммитом** от кода (`vault: ...`). Vault, изменённый во время реализации (план, запись задачи в реестре, заметки, пробы), – на ветке задачи; новые задачи – в `experimental` (2.3)
- Stage по имени файла, **не** `git add .` или `git add -A`
- **Не** упоминай Claude в коммитах (без Co-Authored-By)

Когда коммитить:
- После каждого завершённого шага плана (если шаг затрагивает код)
- После группы мелких связанных шагов (если каждый по отдельности не имеет смысла)
- **Перед** переходом к шагу, который затрагивает другую подсистему
- При обновлении vault — отдельный коммит

### 2.3. Обнаружение новых проблем

В ходе реализации могут всплыть неожиданные проблемы. Новая задача – часть базовой ветки `experimental`, а не ветки задачи. Протокол:

1. **Не уходи в сторону.** Не начинай чинить найденную проблему, если она не в плане
2. **Зарегистрируй в основном каталоге** (`<КОРЕНЬ>\vault\GDM\...`):
   - тип ясен (BUG/DEBT/FEAT/VAL/RES) – запись в реестре по формату существующих записей, статус `🔴 ОТКРЫТ`, в описании «Обнаружено при реализации [[<план>]]»;
   - коммит сразу, в `experimental`, правило 6: `vault: <NEW-ID> зарегистрирован – обнаружено при реализации <ID>`. Реестр – общий файл, коммитится целиком (как в 1.4);
   - тип неясен – короткая заметка в `<КОРЕНЬ>\vault\GDM\inbox\` (разбирается в 4.4):
   ```
   ---
   tags: [inbox, обнаружено-при-реализации]
   date: <дата>
   source: <ID текущей задачи>
   ---
   # <суть проблемы>
   Обнаружено при реализации [[<план>]].
   <описание: что увидел, почему это проблема>
   ```
3. **Оцени блокирует ли** — мешает ли эта проблема завершить текущий шаг?
   - Не блокирует → продолжай план
   - Блокирует → СТОП, сообщи пользователю, предложи варианты:
     a) Обходной путь в рамках плана
     b) Приостановить, создать `/issue` для блокера, вернуться после

### 2.4. Что делать если тесты не проходят

После выполнения шага тесты могут упасть. Алгоритм:

1. **Тест упал из-за текущих изменений** (новый тест или сломан существующий):
   - Исправь в рамках текущего шага
   - Если не удаётся за разумное время (~15 минут) → п.3

2. **Тест упал по не связанной причине** (flaky, известный баг):
   - Проверь — есть ли это в vault (`knowledge/debugging/`, реестр багов)
   - Если известный — продолжай, в сообщении коммита текущего шага добавь примечание: `(тест X flaky, см. BUG-NNN)`

3. **Не удаётся починить:**
   - Изменения остаются незакоммиченными в `<W>` – worktree изолирован; `git stash` не использовать (правило 7)
   - Зарегистрируй проблему как новый BUG/DEBT (2.3)
   - Сообщи пользователю: что сломалось, почему, какие варианты
   - **Не коммить сломанное состояние**

### 2.5. Прогресс

После каждого шага кратко сообщи:
```
Шаг N/M: <название> ✅
  Файлы: <список>
  Тесты: <passed>/<total>, уровень <быстрый | полный> (baseline того же уровня: <baseline>)
  Коммит: <hash> <message>
```

Если шаг занимает много изменений — сообщай промежуточный статус.

### 2.6. Возобновление после прерывания

Если сессия оборвалась (контекст потерян, пользователь вернулся позже):

1. Найди worktree: поле `worktree:` плана или `git worktree list`. Worktree удалён, а ветка есть – восстанови: `git -C <КОРЕНЬ> worktree add .worktrees/<id-lowercase> <branch>` (без `-b`), затем подмодуль и конфигурация CMake – как в 1.5
2. Прочитай план в `<W>` — frontmatter покажет `status: в процессе`
3. `git -C <W> log --oneline experimental..HEAD` — какие шаги уже закоммичены
4. Сопоставь коммиты с шагами плана — определи последний завершённый шаг
5. Проверь `git -C <W> status` — есть ли незакоммиченные изменения (прерванный шаг)
6. Собери в `<W>\build` и прогони быстрый уровень — убедись что текущее состояние зелёное
7. Сними заново снимок основного каталога (правило 2)
8. Продолжи со следующего шага

## Фаза 3: Верификация

После выполнения всех шагов плана.

### 3.1. Чеклист критериев завершения

Пройди чеклист «Критерии завершения» из плана. Для каждого пункта — подтверди или укажи проблему.

### 3.2. Финальная сборка и тесты

Оба конфига — Release и Debug, **строго последовательно** (полный цикл Release, потом полный цикл Debug):

```powershell
cmake --build <W>\build --config Release
ctest --test-dir <W>\build -C Release --output-on-failure
cmake --build <W>\build --config Debug
ctest --test-dir <W>\build -C Debug --output-on-failure
```

Это обязательный полный прогон задачи: после шагов шёл в основном быстрый уровень.

Если тестов > 5 — фильтруй вывод ctest: `| Select-Object -Last 30` или grep по FAILED.

Проверь вывод сборки на warnings (оба конфига). Ноль warnings — критерий успеха. Если warning из внешней библиотеки (amgcl, Eigen, Catch2) — допустимо, но отметь в отчёте.

Сравни с baseline **для каждого конфига**:
- Количество тестов: было → стало
- Время: было → стало
- Новые тесты: какие добавлены
- Warnings: было → стало (новые warnings недопустимы)
- Различия Debug vs Release (если есть — это сигнал о UB или неинициализированной памяти)

Если падает тест, которого задача не касалась, – сначала проверь его на точке ветвления: дерево `<W>` чистое (иначе незакоммиченное уедет вместе с переключением) → `git -C <W> switch --detach $(git -C <W> merge-base experimental HEAD)` → `cmake --build <W>\build --config Release` → `ctest --test-dir <W>\build -C Release -R "<имена упавших тестов>" --output-on-failure` → `git -C <W> switch <branch>` и пересборка. Точка ветвления, а не текущая база: база могла уйти вперёд. Падает и на базе – это дрейф окружения или чужая регрессия: не чинить в рамках задачи, сообщить пользователю. Падает только на ветке – найди виновный шаг по пошаговым коммитам (тот же приём с `git -C <W> switch --detach <коммит шага>`).

### 3.3. Визуальная верификация

Если план предусматривает визуальную верификацию (CSV + анимация/графики):
1. Убедись что CSV-файлы генерируются
2. Убедись что Python-скрипты отрабатывают
3. Результаты — в vault или `<W>\build`; файлы, нужные после задачи, – перед `/merge` в `<КОРЕНЬ>\results\` (правило 9)

### 3.4. Обзор изменений

```powershell
git -C <W> log --oneline experimental..HEAD
git -C <W> diff --stat experimental...HEAD   # три точки – от точки ветвления (1.7): база могла уйти вперёд
```

Проверь:
- [ ] Нет случайных файлов (build артефакты, логи, .vs/)
- [ ] Нет отладочного кода (printf, std::cout для отладки, временные хаки)
- [ ] Нет закомментированного старого кода (легитимный `#ifdef` для экспериментов — допустим, если обоснован в плане)
- [ ] Vault-изменения в отдельных коммитах от кода
- [ ] Основной каталог не содержит твоих правок кода (правило 2)

## Фаза 4: Финализация

Правки журнала и vault этой фазы – в `<W>`, коммит на ветке задачи (кроме 4.4).

### 4.1. Журнал изменений

Каждая задача, изменившая код или тесты (`src/`, `HydroSolver/`, `tests/`, `examples/`, `scripts/`, `CMakeLists.txt`), оставляет пункт в `<W>\CHANGELOG.md`, раздел «## Не выпущено». Журнал читают разработчики и пользователи симулятора без vault. Файла нет – создать с заголовком `# Журнал изменений` и разделом `## Не выпущено`. При выпуске версии раздел переименовывает пользователь в «## X.Y.Z – <дата>». Задача не меняла код (только vault, `.claude/`) – записи нет, в отчёте 4.5: «Журнал: не нужен – код не менялся».

1. **Подраздел** по типу задачи:

   | Тип | Подраздел |
   |---|---|
   | FEAT, VAL | «### Добавлено» |
   | BUG | «### Исправлено» |
   | DEBT | «### Изменено»; «### Удалено» – если суть задачи в удалении |
   | RES | по сути изменения кода: «### Добавлено» или «### Изменено» |

   Подраздела нет – создать; порядок подразделов – «Добавлено», «Изменено», «Исправлено», «Удалено». Пункт – в конец подраздела.
2. **Пункт** – один абзац, 3–8 предложений, по существу:
   ```markdown
   - **<ID>.** <Задача>. <План реализации>. <Результат>.
   ```
   - **Задача** (1–2 предложения) – чего не хватало или что работало неправильно, глазами пользователя симулятора: симптом, условие, при котором он проявлялся.
   - **План реализации** (1–3 предложения) – как решено: подход и затронутые части (класс, модуль, параметр, пример).
   - **Результат** (1–3 предложения) – что изменилось в поведении: новый параметр, режим скважины, вывод, сообщение.
   - Не писать: хеши коммитов, ссылки и пути vault (`[[...]]`, `vault/...`), число тестов, ход реализации по шагам, сведения из плана, не дошедшие до кода. Журнал читают без репозитория и vault.
3. **Проверка:** раздел «## Не выпущено» на месте, пункт – в нужном подразделе.
4. **Коммит** на ветке задачи, отдельно от vault: `git -C <W> commit -m "docs: <ID> – запись в журнале изменений" -- CHANGELOG.md`.

### 4.2. Обновить vault

1. **Реестр** — обновить статус задачи:
   - BUG/DEBT → `известные баги и технический долг.md`: «**Статус:** ✅ исправлено <дата>, не влит – ветка `<branch>` в `.worktrees/<id-lowercase>` (от `<точка ветвления>`, `<первый>`…`<последний коммит>`): <тесты, ключевые числа>»
   - FEAT → `планируемые фичи.md`: `**Статус:** ✅ реализовано <дата>, не влит – …` (то же)
   - VAL → `валидационные кейсы.md`: `**Статус:** ✅ пройден <дата>, не влит – …`
   - RES → `исследования и эксперименты.md`: `**Статус:** ✅ завершён <дата>` или `❌ отвергнуто <дата>`, `не влит – …`

   «Не влит» заменит `/merge`.

2. **План** — обновить frontmatter: `status: реализован`

3. **Knowledge** (если применимо):
   - Исправлен баг → заметка в `knowledge/debugging/` (симптом, причина, фикс)
   - Принято решение → заметка в `knowledge/decisions/`
   - Результат валидации → обновить `knowledge/validation/`
   - Результат эксперимента → заметка с выводом, графиками

4. **Приоритеты** — обновить `vault/GDM/00-home/текущие приоритеты.md` если задача была в приоритетах

5. **Index** — обновить `vault/GDM/00-home/index.md` если созданы новые заметки

6. **Коммит vault-изменений** — отдельно: `vault: результаты <ID> <краткое описание>`

### 4.3. Прокомментировать GitHub issue

Если есть GitHub issue (поле `github` в frontmatter плана): сохрани текст комментария в `<W>\vault\GDM\issues\<id-lowercase>\05-comment-done.md` (папка проекта, не scratchpad – см. «Файлы для `gh --body-file`» в `/issue`), закоммить на ветке задачи (вместе с 4.2 или отдельно, `vault:`) и отправь:

```powershell
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User"); gh issue comment <N> --repo ArturSalamatin/GDM --body-file <W>\vault\GDM\issues\<id-lowercase>\05-comment-done.md
```

**Не закрывай issue** — его закрывает `/merge`. Формат комментария – заголовок `## Реализация завершена`, строки «**Ветка:** `<branch>` (worktree `.worktrees/<id-lowercase>`, от `experimental` `<точка ветвления>`)», «**План:** `vault/GDM/plans/<файл>`», затем результат по типу:
- BUG: `Реализовано в ветке <branch>. Причина: <причина>. Тесты: <N> passed. Готово к merge.`
- DEBT: `Реализовано в ветке <branch>. Тесты: <N> passed. Готово к merge.`
- FEAT: `Реализовано в ветке <branch>. Новые тесты: <список>. Всего тестов: <N>. Готово к merge.`
- VAL: `Реализовано в ветке <branch>. Метрика: <значение> < <tolerance>. Готово к merge.`
- RES: `Реализовано в ветке <branch>. Вывод: <гипотеза подтверждена/отвергнута>. Готово к merge.`

### 4.4. Новые проблемы

Задачи, зарегистрированные по 2.3, уже в `experimental`. Если остались заметки в `<КОРЕНЬ>\vault\GDM\inbox\` с неясным типом:
1. Для каждой заметки: определи тип (BUG/DEBT/FEAT/VAL/RES)
2. Добавь в соответствующий реестр с новым ID
3. Удали из inbox
4. Коммит в `experimental`, правило 6

Сообщи пользователю: «Обнаружено N новых проблем: <список>». Предложи `/issue` для формализации на GitHub.

### 4.5. Сообщить результат

Перед отчётом: `git -C <W> status --porcelain` пуст – `/merge` удаляет только чистый worktree.

```
## Результат /implement <ID>

**Статус:** ✅ реализовано / ⚠️ частично / ❌ заблокировано

**Ветка:** <branch> (worktree .worktrees/<id-lowercase>, от <точка ветвления>)
**Коммиты:** <N> (<список хешей>)
**Журнал:** пункт <ID> в «Не выпущено», подраздел «<подраздел>» | не нужен – код не менялся
**Тесты (Release):** <baseline> → <итог> (+<новых>)
**Тесты (Debug):** <baseline> → <итог>
**Warnings:** <baseline> → <итог> (ноль — цель)

**Что сделано:**
- <пункт 1>
- <пункт 2>

**Vault обновлён:**
- <список файлов>

**Новые проблемы:** <список или «нет»>

**Следующие шаги:**
- Проверь изменения: `git log --oneline experimental..<branch>`, `git diff --stat experimental...<branch>`
- Влитие: скажи «мерж» или `/merge <ID>` – push ветки задачи, мерж `--no-ff` в `experimental`, worktree удаляется (ветка остаётся), push `experimental`
```

## Протокол отката

Если реализация зашла в тупик (сборка сломана и не чинится, тесты массово падают, блокирующая проблема):

1. **Не коммить сломанное состояние** кода
2. Незакоммиченные изменения остаются в `<W>` – `git stash` не использовать (правило 7)
3. Обнови frontmatter плана в `<W>`: `status: заблокирован`, добавь `blocker: <описание>`
4. Коммит на ветке задачи – только план: `git -C <W> commit -m "vault: <ID> заблокирован – <причина>" -- <план>`
5. Блокер – новая задача в `experimental` (2.3)
6. Сообщи пользователю: что пошло не так, на каком шаге, какие варианты
7. Не используй `git checkout --` или `git reset` без явного разрешения пользователя

## Примечания

- Язык: русский
- Делать ТОЛЬКО то, что в плане. Улучшения «по дороге» → inbox, не в код
- Коммиты частые и самодостаточные. Каждый компилируется и тесты зелёные
- Vault-изменения отдельным коммитом от кода
- Stage по имени файла, не `git add .`
- Не упоминай Claude в коммитах
- **Не пушь и не мержь сам** – push ветки задачи и `experimental`, влитие `--no-ff` делает `/merge` по слову пользователя «мерж». Влитие experimental → dev → main – вручную пользователем
- При ошибке сборки — исправляй и пересобирай автоматически, без запроса подтверждения
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
