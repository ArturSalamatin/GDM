# /plan-fix — план исправления бага

Аргумент: `$ARGUMENTS` — идентификатор бага (например `BUG-001`, `BUG-002`) или номер GitHub issue (например `#1`).

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

---

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

Проверь, есть ли уже план для этого ID:
```
ls vault/GDM/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю путь и спроси: обновить существующий или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/GDM` → из title извлеки ID (формат: `BUG-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/GDM/roadmap/известные баги и технический долг.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM` (там детальный анализ, варианты решения, комментарии)
3. Прочитай подробную заметку из `knowledge/debugging/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Извлечь имя ветки

Имя ветки генерируется командой `/issue`. Найди его:
1. В GitHub issue (в разделе плана решения или комментариях)
2. Или в vault-записи
3. Если ветки нет — сгенерируй: `fix/<id-lowercase>/<slug-2-5-слов>`
4. Проверь, не существует ли уже такая ветка: `git branch --list "<имя>"`

### 1.4. Загрузить связанные заметки

1. Из подробной заметки найди все wiki-ссылки `[[...]]`
2. Прочитай каждую связанную заметку (physics, numerics, decisions)
3. Проверь, есть ли связанные BUG/DEBT/FEAT/VAL/RES — прочитай их тоже (один баг часто связан с другим)
4. Прочитай `vault/GDM/roadmap/стратегия тестирования GDM.md` — паттерны тестов
5. Прочитай `vault/GDM/roadmap/инвентаризация кодовой базы*.md` — какие модули затронуты

### 1.5. Исследовать код

Для каждого файла, упомянутого в задаче:

1. **Валидация:** проверь, что файл существует, строки актуальны
2. **Контекст:** Read окрестности ±30 строк от проблемного места
3. **Вызовы вверх:** grep — кто вызывает проблемную функцию?
4. **Вызовы вниз:** что вызывается из проблемного кода?
5. **Аналогичные паттерны:** есть ли в проекте похожий механизм, который уже работает правильно и может служить образцом?
6. **Существующие тесты:** grep по именам функций в `tests/` — что уже покрыто?
7. **Инварианты:** какие физические/математические свойства должны соблюдаться? (определи из vault-заметок и кода)
8. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности» — модули, API, поведение, которые фикс не должен затрагивать

## Фаза 2: Анализ и проработка

### 2.1. Воспроизведение бага

Описать чётко:
- Какой тест воспроизводит баг (имя, тег, файл)
- Команда запуска: `ctest --test-dir build -C Release -R "<pattern>"`
- Ожидаемое поведение vs фактическое
- Если теста нет — описать, как создать минимальный воспроизводящий тест

### 2.2. Цепочка причинно-следственных связей

Построить полную цепочку от триггера до проявления:
1. Что вызывает проблему (входные данные, состояние, последовательность вызовов)
2. Где именно возникает ошибка (файл, строка, переменная)
3. Как ошибка распространяется (propagation path)
4. Где проявляется (exception, NaN, зависание, неверный результат)

### 2.3. Целевое состояние

Кратко опиши, как должен вести себя код после фикса:
- Ожидаемое поведение в сценарии, где раньше был баг
- Какие тесты должны стать зелёными
- Какие инварианты должны соблюдаться

### 2.4. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** — что именно менять, в каких файлах
- **Конкретные изменения** — псевдокод или diff-like описание
- **Плюсы/минусы** — trade-offs
- **Риски** — что может пойти не так
- **Совместимость** — ломает ли что-то существующее?
- **Трудоёмкость** — количество файлов, примерное число строк

### 2.5. Выбор варианта

Обоснуй выбор. Если варианты комбинируются (например: quick fix + архитектурное решение) — объясни порядок и зависимости.

### 2.6. Поиск подводных камней

Для выбранного варианта пройди чеклист. Для каждого пункта отметь:
✅ проверено, безопасно | ⚠️ есть риск, адресован в шаге N | ❌ проблема, требует решения

- [ ] **Побочные эффекты:** grep по имени изменяемых функций — вызываются ли из других мест?
- [ ] **Потокобезопасность:** выполняется ли код внутри `#pragma omp parallel`? Shared state?
- [ ] **Граничные случаи:** нулевые значения, пустые контейнеры, деление на ноль, NaN, первая/последняя итерация
- [ ] **Производительность:** аллокации внутри горячих циклов (Newton loop, assembly, solve)?
- [ ] **Обратная совместимость:** изменится ли поведение для рабочих сценариев?
- [ ] **Порядок вызовов:** зависимость от порядка инициализации?
- [ ] **Состояние при ошибке:** throw/early return — объект остаётся в валидном состоянии?
- [ ] **Численная устойчивость:** tolerance, overflow/underflow, catastrophic cancellation
- [ ] **Связь с другими задачами:** конфликт с обходами/фиксами других BUG/DEBT/FEAT/VAL/RES?
- [ ] **Зависимости сборки:** include-ы, CMakeLists.txt, порядок линковки

### 2.7. Обнаружение новых проблем

В ходе анализа могут обнаружиться новые проблемы. Для каждой:
1. Зафиксируй в плане (раздел «Обнаруженные проблемы»)
2. Блокирует ли текущую задачу? Если да — включи в план как предварительный шаг
3. Если нет — после завершения плана добавь в соответствующий реестр (`известные баги и технический долг.md`, `планируемые фичи.md`, `валидационные кейсы.md` или `исследования и эксперименты.md`)

## Фаза 3: Детализация плана

### 3.1. Этапы для бага

1. **Подготовка** — создать ветку, собрать проект, воспроизвести баг
2. **Минимальный фикс** — наименьшее изменение, чтобы тест стал зелёным
3. **Тесты минимального фикса** — новые тесты + снять скрытые теги `[.]`
4. **Архитектурное решение** — правильная реализация (если отличается от quick fix)
5. **Тесты архитектуры** — unit + integration + regression
6. **Верификация** — сравнение с аналитикой/эталоном, визуальная проверка, CSV export
7. **Очистка** — удалить ненужные workaround-ы, обновить vault, закрыть issue

Если минимальный фикс = архитектурное решение — объедини этапы 2–3 и 4–5.

### 3.2. Структура шага

Каждый шаг — атомарная единица работы (~50 строк изменений максимум).

```
### Шаг N: <название>

**Цель:** одно предложение — зачем этот шаг нужен

**Файлы:** <полные пути от корня проекта>

**Контекст:**
Для читателя без контекста сессии: что делает текущий код,
почему это проблема, что хотим получить.
Ссылки на vault-заметки: [[имя заметки]].
Термины расшифрованы при первом упоминании.

**Что сделать:**
1. В файле `X.cpp`, функция `Y()`, строка ~N:
   конкретное действие
2. ...

**Изменения (старый → новый код):**

До:
    <текущий код>

После:
    <новый код>

**Проверка после этого шага:**
- Сборка: `cmake --build build --config Release`
- Тест: `ctest --test-dir build -C Release -R "<name>"`
- Ожидаемый результат: <конкретно>
- Регрессия: `ctest --test-dir build -C Release` (все тесты зелёные)

**Подводные камни:**
- <ссылки на пункты чеклиста из 2.6>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Тестовая стратегия

Для бага тесты строятся вокруг:

1. **Тест-воспроизводитель:** воспроизводит именно этот баг. Без фикса — падает, с фиксом — зелёный
2. **Граничные тесты:** проверяют edge cases вокруг бага (нулевые значения, экстремальные параметры)
3. **Инвариантные тесты:** физические свойства, которые должны соблюдаться всегда
4. **Regression:** существующие тесты, которые не должны сломаться (перечислить конкретно)
5. **Visual:** CSV + анимация для ключевых сценариев (если применимо)

Формат описания теста:
```
**Тест:** <название Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp (существующий / новый)
**Сценарий:** <что проверяем — на уровне физики>
**Setup:** <сетка, начальные условия, граничные условия>
**Ожидание:** <конкретные числа, неравенства, или качественные свойства>
**Baseline:** <с чем сравниваем — если применимо>
**Backward compat:** <при каком параметре=0 проверяется — если применимо>
**Предотвращает:** <какой класс ошибок этот тест ловит>
```

### 3.4. Критерии завершения

Чеклист «задача решена когда»:
- [ ] Тест-воспроизводитель зелёный
- [ ] Все новые тесты зелёные
- [ ] Все существующие тесты зелёные (`ctest --test-dir build -C Release`)
- [ ] Визуальная верификация пройдена (если применимо)
- [ ] Скрытые теги `[.]` сняты
- [ ] Workaround-ы удалены (если стали не нужны, или объяснено почему оставлены)
- [ ] Vault обновлён: запись в техдолге → статус, заметка в debugging
- [ ] GitHub issue закрыт с комментарием о решении (если создан)
- [ ] Roadmap фаза обновлена (если баг блокировал задачу фазы)

### 3.5. Загрузка контекста при реализации

В начале файла плана добавь секцию:

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Создай ветку: `git checkout -b <branch>`
4. Собери проект: `cmake -B build -S . -G "Visual Studio 17 2022"; if ($?) { cmake --build build --config Release }`
5. Прогони тесты (baseline): `ctest --test-dir build -C Release`
6. Запомни количество тестов и время — это baseline
7. Воспроизведи баг: `ctest --test-dir build -C Release -R "<test>"`
8. Начни с шага 1. После каждого шага: сборка + тесты
```

## Фаза 4: Верификация плана (3 раунда)

### Раунд 1: Полнота

- [ ] Каждый файл из «Затронутые файлы» упомянут хотя бы в одном шаге
- [ ] Для каждого шага есть проверка (тест или команда)
- [ ] Зависимости шагов не образуют циклов
- [ ] Все подводные камни (2.6) адресованы в конкретных шагах
- [ ] Тестовая стратегия: тест-воспроизводитель + граничные + инварианты + regression
- [ ] Критерии завершения полны и проверяемы
- [ ] После каждого шага проект компилируется и тесты зелёные

### Раунд 2: Корректность

Общее (для каждого шага):
- [ ] Упомянутые методы/поля/типы существуют (grep)
- [ ] Типы совместимы
- [ ] Номера строк актуальны (перепроверь grep-ом)

Специфичное для бага:
- [ ] Новый код не нарушает существующие инварианты
- [ ] Уравнения корректны (если баг затрагивает физику: дискретизация, производные, знаки)
- [ ] CMake-изменения корректны (если баг затрагивает сборку: target_sources, include_directories)

### Раунд 3: Автономность

Представь: Claude в новой сессии с compact-сжатым контекстом открывает этот план.

- [ ] Каждый шаг самодостаточен — нет ссылок на «то, что обсуждали»
- [ ] Полные пути к файлам от корня проекта
- [ ] Объяснено ПОЧЕМУ, а не только ЧТО
- [ ] Физический/математический контекст на месте (формулы, ссылки на vault)
- [ ] Термины расшифрованы при первом упоминании
- [ ] Секция «Как начать работу» содержит конкретные команды
- [ ] Baseline зафиксирован (количество тестов, время)

Если обнаружены проблемы — исправь план и повтори раунд.

## Фаза 5: Сохранение

### 5.1. Создать файл плана

Путь: `vault/GDM/plans/<id-lowercase> <slug>.md`

Frontmatter:
```yaml
---
tags:
  - план
  - баг
date: <дата>
issue: <ID>
github: <номер issue или null>
branch: <имя ветки>
status: готов к реализации
---
```

### 5.2. Обновить связи

1. В записи техдолга: `- **План:** [[<имя плана>]]`
2. Если есть GitHub issue: `gh issue comment <N> --repo ArturSalamatin/GDM --body "План: vault/GDM/plans/<файл>. Ветка: <branch>. Шагов: <N>."`
3. В `vault/GDM/00-home/index.md` — добавь план в секцию Plans

### 5.3. Зафиксировать новые проблемы

Для каждой проблемы из фазы 2.7:
1. Добавь в соответствующий реестр с новым ID
2. Укажи «Обнаружено при анализе <ID>»

### 5.4. Сообщить результат

- Путь к файлу плана
- Количество этапов и шагов
- Обнаруженные новые проблемы (если есть)
- Имя ветки
- Оценка: файлов, строк, суммарное время

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Файл плана должен быть ДЛИННЫМ и ПОДРОБНЫМ. Избыточность лучше недосказанности
- Если >15 шагов — предложи разбить на под-задачи со своими планами
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
