# /audit-plan — аудит плана перед реализацией

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `BUG-007`, `FEAT-003`, `VAL-001`, `DEBT-005`, `RES-002`).

Результат: план проверен по 7 измерениям, найденные проблемы исправлены в файле плана, пользователю выдан отчёт.

**Когда запускать:** после `/plan-fix`, `/plan-improve`, `/plan-feature`, `/plan-validate`, `/plan-research` — перед `/implement`.

**Принцип:** команда — скептик, а не подтверждатель. Задача — найти то, что сломает реализацию.

---

## Фаза 1: Загрузка плана

### 1.1. Найти план

```
ls vault/GDM/plans/<id-lowercase>*
```

Если план не найден — СТОП:
```
План для <ID> не найден. Сначала создай план:
- BUG → /plan-fix <ID>
- DEBT → /plan-improve <ID>
- FEAT → /plan-feature <ID>
- VAL → /plan-validate <ID>
- RES → /plan-research <ID>
```

### 1.2. Проверить статус

Из frontmatter:
- `готов к реализации` → аудит уместен, продолжай
- `в процессе` → предупреди: «План уже в реализации. Аудит может привести к правкам, конфликтующим с текущей работой. Продолжить?»
- `реализован` / `отменён` → СТОП, сообщи: «План в статусе <статус>, аудит не нужен»

Проверь поле `audit:` в frontmatter. Если аудит уже проводился — сообщи: «План уже проходил аудит <дата>. Провести повторный?» При повторном аудите — перезаписать поле `audit:`, не дублировать

### 1.3. Прочитать план целиком

Прочитай файл плана от начала до конца. Запомни:
- Тип задачи (BUG/DEBT/FEAT/VAL/RES)
- Количество этапов и шагов
- Список затронутых файлов
- Имя ветки
- Тестовую стратегию
- Критерии завершения

### 1.4. Загрузить связанный контекст

**Из плана (явные ссылки):**

1. Все vault-заметки, на которые ссылается план (`[[...]]`). Для каждой ссылки — проверь что файл существует. Битая ссылка = находка 🟡
2. Запись в соответствующем реестре roadmap
3. GitHub issue (если указан в frontmatter): `gh issue view <N> --repo ArturSalamatin/GDM`
4. `vault/GDM/roadmap/стратегия тестирования GDM.md`

**Активный поиск (контекст, который план мог пропустить):**

5. По каждому затронутому файлу/модулю — проверь, есть ли в vault заметки, которые план НЕ ссылается, но должен:
   - `vault/GDM/atlas/` — описание затронутого модуля
   - `vault/GDM/knowledge/physics/` — если план затрагивает физику
   - `vault/GDM/knowledge/numerics/` — если план затрагивает численные методы
   - `vault/GDM/knowledge/debugging/` — были ли похожие баги раньше? Grep по ключевым словам задачи
   - `vault/GDM/knowledge/decisions/` — есть ли решения, которые объясняют, почему код устроен так, как сейчас? (план может «исправлять» намеренное поведение)
6. Проверь `vault/GDM/roadmap/известные баги и технический долг.md` — есть ли другие BUG/DEBT, затрагивающие те же файлы? Если да — проверь, не конфликтуют ли планы

## Фаза 2: Аудит по 7 измерениям

**Порядок важен.** Измерения 1–2 — фундамент. Если измерение 1 находит критические проблемы (файл не существует, метод удалён), то в измерениях 2–6 пропускай чеки для затронутых шагов — они заведомо невалидны, пока не починен фундамент. Измерение 0 выполняется всегда.

Для каждого измерения — пройти все чеки, зафиксировать проблемы. Формат находки:

```
- 🔴/🟡/🔵 **[Измерение N, шаг M]** <суть проблемы>
  > <цитата из плана — строка, которая неверна>
  **Риск:** <что сломается при реализации>
  **Фикс:** <конкретное исправление или «требует решения пользователя»>
```

Для 🔵 мелких — допустим однострочный формат без цитаты и риска.

### Измерение 0: Соответствие исходной задаче и верность анализа

Сравни план с первоисточником задачи — запись в vault roadmap + GitHub issue + заметка в knowledge. Затем перепроверь анализ по коду.

**0A. Соответствие задаче:**

1. **Корневая причина.** Для BUG: план атакует именно ту причину, которая описана в задаче? Или чинит симптом / смежную проблему?
2. **Полнота скоупа.** Все ли аспекты задачи покрыты планом? Если issue описывает 3 проявления бага — план должен адресовать все 3, а не одно
3. **Избыточность скоупа.** Не делает ли план больше, чем просит задача? (рефакторинг «по дороге», расширение API, которое не требовалось)
4. **Критерии завершения vs задача.** Критерии из плана — действительно означают «задача решена»? Или план может быть «выполнен» при живом баге?
5. **Приоритеты.** Если задача связана с текущей фазой в `vault/GDM/00-home/текущие приоритеты.md` — план не противоречит направлению фазы?

**0B. Верность анализа причин (для BUG/DEBT):**

Не доверяй анализу в плане на слово — перепроверь по коду.

1. **Цепочка причинно-следственных связей.** План описывает «триггер → место ошибки → распространение → проявление». Пройди по этой цепочке в коде: действительно ли триггер вызывает описанный эффект? Нет ли другого пути распространения, который план не учитывает?
2. **Выбор варианта решения.** План описывает N вариантов и выбирает один. Проверь:
   - Отвергнутые варианты действительно имеют описанные минусы? (а не отвергнуты ради упрощения)
   - Выбранный вариант действительно имеет описанные плюсы?
   - Нет ли варианта, который план вообще не рассмотрел?
3. **Место фикса.** Правильное ли место в коде выбрано для исправления? Может быть, проблему лучше решить выше/ниже по call stack? Фикс в месте проявления vs фикс в месте причины — план должен объяснить выбор

### Измерение 1: Корректность ссылок на код и синтаксис

Для КАЖДОГО шага плана:

**1A. Ссылки:**

1. **Файлы существуют.** Grep/Glob каждый файл из поля «Файлы»
2. **Методы/поля/типы существуют.** Grep каждый упомянутый идентификатор в кодовой базе
3. **Номера строк актуальны.** Если шаг ссылается на «строка ~N» — проверь grep-ом, что код на этой строке соответствует описанию. Допуск: ±10 строк. Если сдвиг > 10 — проблема
4. **Сигнатуры совпадают.** Если шаг модифицирует вызов функции — проверь текущую сигнатуру (параметры, типы возврата)
5. **Include-ы.** Если шаг добавляет `#include` — проверь что заголовок существует
6. **CMake.** Если шаг меняет CMakeLists.txt — проверь что упомянутые target-ы и source-файлы существуют

**1B. Синтаксическая корректность блоков «После:»:**

Блоки «После:» — это код, который будет вставлен в файл. Проверь каждый:

1. **Типы совместимы.** Переменные, параметры, возвращаемые значения — типы сходятся с окружающим кодом? Read окрестности ±20 строк от места вставки
2. **Области видимости.** Используемые переменные объявлены и доступны в scope вставки?
3. **Шаблоны и концепты.** Если код использует шаблонные типы — инстанциация корректна?
4. **const-correctность.** Метод помечен const — а новый код модифицирует состояние?
5. **Незакрытые скобки / блоки.** Баланс `{}`/`()`/`<>` корректен после вставки?
6. **Стиль.** Код в блоке «После:» стилистически совпадает с окружающим кодом (naming, indentation, braces)?

### Измерение 2: Логическая целостность

1. **Зависимости шагов.** Построй граф зависимостей. Проверь:
   - Нет циклов
   - Каждый шаг, указанный в «Требует», действительно предшествует
   - Нет неявных зависимостей (шаг B использует результат шага A, но зависимость не указана)
2. **Полнота покрытия файлов.** Каждый файл из списка «Затронутые файлы» должен быть упомянут хотя бы в одном шаге. И наоборот: каждый файл, модифицируемый в шагах, должен быть в списке
3. **Согласованность «До/После».** Для первого шага, затрагивающего файл — блок «До:» должен соответствовать текущему состоянию файла на диске (grep/read). Для последующих шагов, затрагивающих тот же файл — «До:» должен отражать состояние **после** предыдущего шага (иначе `Edit` не найдёт `old_string`)
4. **Кумулятивный эффект.** Если несколько шагов правят один файл — проверь, что правки не конфликтуют
5. **Пробелы.** Есть ли разрыв между описанием проблемы (фаза 2 плана) и предложенными шагами (фаза 3)? Все ли аспекты проблемы покрыты?

### Измерение 3: Физика и математика

Применимо только если план затрагивает уравнения, дискретизацию, физические модели.

1. **Знаки.** Проверь знаки в дискретных уравнениях (gradient, divergence, source terms)
2. **Размерности.** Проверь согласованность единиц измерения в формулах
3. **Граничные условия.** Правильно ли обрабатываются краевые ячейки / скважинные ячейки
4. **Устойчивость.** Не нарушает ли изменение CFL-подобные ограничения или условия устойчивости
5. **Законы сохранения.** Сохраняется ли баланс масс после изменения
6. **Вырожденные случаи.** Деление на ноль, Sw=0, Sw=1, нулевые проницаемости, один пласт, одна скважина
7. **Соответствие литературе.** Если план ссылается на формулу из статьи/книги — проверь что формула верно переписана

### Измерение 4: Тестовая стратегия

**4A. Полнота тестов:**

1. **Покрытие.** Для каждого изменения в коде — есть ли тест, который его верифицирует?
2. **Тест-воспроизводитель** (для BUG). Описан ли тест, который падает без фикса и проходит с фиксом?
3. **Edge cases.** Проверены ли граничные случаи из измерения 3 (нули, экстремальные значения, вырожденные конфигурации)?
4. **Regression.** Перечислены ли конкретно тесты, которые не должны сломаться?
5. **Visual.** Предусмотрен ли CSV export + визуализация для ключевых сценариев?
6. **Tolerance.** Если в тестах есть числовые tolerance — обоснованы ли они? Слишком мягкие (всё проходит) или слишком жёсткие (ложные падения)?
7. **Негативные тесты.** Если код должен корректно обрабатывать невалидные входы — есть ли тесты на это?

**4B. Реализуемость тестов:**

8. **Инфраструктура.** Если тест описывает сравнение с аналитическим решением, эталоном, MRST-результатом — существует ли в коде механизм для этого? (функция аналитического решения, pointwise-сравнение, импорт эталонных данных). Если нет — план должен включать шаг создания инфраструктуры
9. **Существующие тесты в «Проверка после шага».** Для каждого шага: тест, указанный в секции «Проверка», существует? Grep по имени теста в `tests/`. Если тест ещё не создан (создаётся в более позднем шаге) — убедись, что порядок шагов это учитывает
10. **Что именно тест проверяет.** Если шаг ссылается на существующий тест как проверку — прочитай тест. Действительно ли он проверяет то, что утверждает план? Или тест проверяет другой аспект?

### Измерение 5: Подводные камни, риски и новые проблемы

**5A. Перепроверка чеклиста плана:**

1. **Чеклист подводных камней из плана.** Найди в плане раздел «Поиск подводных камней» (нумерация раздела зависит от типа плана — ищи по заголовку, не по номеру). Пройди каждый пункт повторно. Отметки ✅ — перепроверь: действительно ли безопасно?
2. **Отсутствующие пункты.** Чего НЕТ в чеклисте, но должно быть? (Специфичные для данной задачи риски)

**5B. Побочные эффекты (не создаёт ли план новые проблемы):**

Для КАЖДОЙ функции/класса/метода, которые план модифицирует:

3. **Все вызывающие.** Grep по имени — кто вызывает? Прочитай каждый call site (±5 строк). Изменение сигнатуры, семантики возврата, побочных эффектов — сломает ли вызывающий код? Если план меняет поведение функции — все ли call sites корректно работают с новым поведением?
4. **Контракты и предусловия.** Вызывающий код может полагаться на неявные гарантии: «функция всегда возвращает >0», «вектор всегда непустой», «вызывается только после init()». Не нарушает ли план эти контракты?
5. **Обходные пути.** Grep по BUG/DEBT/workaround/hack/TODO/FIXME в файлах, затронутых планом. Есть ли workaround-ы, которые зависят от текущего (ошибочного) поведения? Фикс бага может сломать обходной путь в другом месте
6. **Каскадные эффекты.** Если план меняет структуру данных (добавляет/удаляет поле, меняет тип) — grep по типу структуры, найди все места сериализации, копирования, сравнения. Все ли обновлены в плане?
7. **Параллельные пути вычисления.** Если план меняет единицы, размерность или способ вычисления величины — найди ВСЕ альтернативные пути, где та же величина вычисляется другим способом (диагностика, баланс масс, вывод в файл, логирование). Если основной путь (rhs/Jacobian) изменён, а проверочный (MassBalance, CurOilDebit_Num) — нет, невязка неизбежна. Прецедент: BUG-020, где фикс единиц в SetRefWellPressure не был доведён до BalanceOil/CurOilDebit_Num → невязка баланса масс 0.15%

**5C. Системные риски:**

7. **Потокобезопасность.** Если изменяемый код внутри OpenMP-параллельных секций — race conditions? Grep по `#pragma omp` в файле и вызывающих
8. **Связь с другими задачами.** Проверь текущие приоритеты и roadmap — нет ли конфликта с другими задачами в работе? Проверь другие ветки: `git branch --list "fix/*" "feat/*" "val/*"` — может ли параллельная работа конфликтовать?
9. **Неожиданные зависимости.** Пройди по `#include`-цепочке — не тянет ли изменение за собой пересборку большой части проекта?
10. **Регрессия производительности.** Если план добавляет вычисления в горячий цикл (Newton iteration, assembly, solve) — оценена ли стоимость? Аллокации в цикле? Лишние копирования?

### Измерение 6: Автономность и читаемость

Представь: Claude в новой сессии, compact-сжатый контекст, никаких воспоминаний о текущем разговоре.

1. **Самодостаточность шагов.** Каждый шаг понятен без контекста предыдущих?
2. **Термины.** Все специфические термины расшифрованы при первом упоминании?
3. **ПОЧЕМУ vs ЧТО.** Объяснена ли причина каждого изменения, а не только действие?
4. **Физический контекст.** Есть ли необходимые формулы, ссылки на vault и литературу?
5. **Полные пути.** Все пути к файлам — от корня проекта?
6. **Секция «Как начать».** Содержит ли конкретные команды (сборка, тесты, воспроизведение)?
7. **Baseline.** Зафиксированы ли количество тестов и время?
8. **Порядок чтения.** Можно ли читать план сверху вниз без возврата? Нет ли forward references на шаги, которые описаны позже?

### Мысленный прогон (после всех измерений)

Пройди план от шага 1 до последнего шага, моделируя состояние кода после каждого шага.

Для каждого шага:
1. Применить блок «После:» мысленно к текущему состоянию файла
2. Проверить: код компилируется? (типы, includes, scope)
3. Проверить: тесты, указанные в «Проверка после шага», пройдут?
4. Обновить «текущее состояние» — следующий шаг работает с результатом предыдущего

Что ловит мысленный прогон:
- **Порядковые ошибки:** шаг 3 ожидает результат шага 5
- **Кумулятивные конфликты:** шаг 2 и шаг 4 правят один метод, но шаг 4 не учитывает изменений шага 2
- **Разрыв компилируемости:** после шага N код не собирается, а тесты запланированы только в шаге N+2
- **Неполнота:** после последнего шага код в целевом состоянии? Все ли изменения, необходимые для решения задачи, выполнены?
- **Адекватность оценок.** Для каждого шага: оценка «~N строк» соответствует реальному объёму работы? Если шаг затрагивает 3 файла с каскадными правками, а оценка — «~5 строк» — автор недооценивает скоуп, что сигнализирует о пропущенных изменениях. Пересчитай оценку по числу найденных мест, требующих правки

Если прогон обнаруживает проблемы — зафиксируй как находки соответствующего измерения (обычно измерение 2 — логическая целостность).

## Фаза 3: Исправление плана

### 3.1. Приоритизация

Отсортируй находки:
1. 🔴 Критические — план нереализуем без фикса (несуществующий файл, неверная формула, отсутствующий тест-воспроизводитель)
2. 🟡 Существенные — реализация возможна, но высок риск ошибки (устаревшие строки, неявные зависимости, слабые тесты)
3. 🔵 Мелкие — качество плана страдает, но реализация не пострадает (терминология, форматирование, недостающий контекст)

### 3.2. Автоматическое исправление

Исправь в файле плана все найденные проблемы. Принцип: если аудит нашёл проблему и знает, как её решить — исправляй, не перекладывай на пользователя.

**Исправлять (механические правки):**
- Устаревшие номера строк → обновить на актуальные (grep)
- Переименованные методы/поля/типы → исправить имена на текущие
- Расхождения «До/После» с реальным кодом → обновить блоки «До:»
- Неуказанные зависимости между шагами → добавить в поле «Зависимости»
- Недостающие файлы в списке «Затронутые файлы» → добавить
- Ошибки порядка шагов, обнаруженные мысленным прогоном → переупорядочить
- Синтаксические ошибки в блоках «После:» (типы, scope, const) → исправить код

**Исправлять (содержательные дополнения — аудит знает ответ):**
- Неполные «Подводные камни» → дополнить чеклист находками из аудита
- Недостающие тесты на edge cases → добавить описания тестов в тестовую стратегию, добавить шаги реализации тестов
- Недостающие вызывающие, которых план не учёл → добавить шаги обновления call sites
- Обходные пути (workaround-ы), которые сломает фикс → добавить шаг удаления/обновления workaround-а
- Каскадные эффекты (сериализация, копирование) → добавить шаги
- Недостающий контекст для автономности → дополнить секции «Контекст» в шагах
- Формулы: очевидные опечатки (знак, индекс) → исправить. Если неуверен — НЕ исправляй, отметь в отчёте

**НЕ исправлять (только отметить в отчёте с пометкой «🔴 требует решения пользователя»):**
- Принципиальные ошибки в анализе причин (план чинит не ту проблему)
- Неверный выбор варианта решения (отвергнутый вариант был лучше)
- Спорные физические/математические решения, в которых аудит не уверен
- Конфликт с параллельной работой на другой ветке (решение — за пользователем)
- Блокирующие баги, которые делают план нереализуемым

### 3.3. Метка аудита

После исправления добавь в frontmatter плана:

```yaml
audit:
  date: <дата>
  findings: <N критических> / <N существенных> / <N мелких>
  auto-fixed: <N>
  manual-required: <N>
```

## Фаза 5: Обновление GitHub issue

Если в frontmatter плана поле `github:` отсутствует или равно `null` — пропусти эту фазу.

### 5.1. Проверить повторный аудит

Прочитай комментарии issue:
```powershell
gh issue view <N> --repo ArturSalamatin/GDM --comments
```

Если уже есть комментарий с заголовком `## Аудит плана` — это повторный аудит. Не добавляй новый комментарий, а **обнови существующий** через `gh api`:
```powershell
gh api repos/ArturSalamatin/GDM/issues/comments/<comment_id> -X PATCH -f body="<новый текст>"
```

Если комментария с аудитом нет — создай новый.

### 5.2. Прокомментировать результат аудита

```powershell
gh issue comment <N> --repo ArturSalamatin/GDM --body "<комментарий>"
```

Формат комментария:

```
## Аудит плана

🔴 Критические: <N> | 🟡 Существенные: <N> | 🔵 Мелкие: <N>
Автофикс: <N> | Требует решения: <N>

### Исправлено автоматически
- <пункт>
- ...

### Требует решения
- <пункт>
- ...

**Вердикт:** ✅ готов к реализации / ⚠️ условно готов / ❌ не готов
```

Если критических = 0 и требующих решения = 0, комментарий короткий:
```
## Аудит плана

✅ План проверен, проблем не найдено. Готов к `/implement`.
```

### 5.3. Добавить label (если есть критические проблемы)

Если вердикт ❌ (не готов):
```powershell
gh issue edit <N> --repo ArturSalamatin/GDM --add-label "needs-rework"
```

Если вердикт ✅ (готов) и label `needs-rework` стоит — снять:
```powershell
gh issue edit <N> --repo ArturSalamatin/GDM --remove-label "needs-rework"
```
