# /issue — создать GitHub issue из записи в vault

Аргумент: `$ARGUMENTS` — идентификатор записи (например `BUG-001`, `BUG-002`, `DEBT-007`) **или** свободный текст описания новой проблемы. Флаг `--dry` в начале аргументов включает dry-run режим.

## Определение режима

- Если `$ARGUMENTS` начинается с `--dry` — режим **dry-run**: выполнить все шаги анализа, показать что будет создано (title, labels, первые строки body, имя ветки), но НЕ создавать issue, НЕ менять vault. Оставшаяся часть аргументов — ID или свободный текст.
- Если аргумент (после `--dry`, если есть) соответствует паттерну `BUG-NNN` или `DEBT-NNN` — режим **existing**: найти запись в vault и создать issue по ней.
- Иначе — режим **new**: создать запись в vault с новым ID и одновременно создать issue.

---

## Режим existing

### 1. Проверка дубликатов на GitHub

Перед любой работой проверь, нет ли уже issue для этого ID:

```
gh issue list --repo ArturSalamatin/GDM --search "<ID>" --state all
```

Если issue уже существует — сообщи пользователю URL и спроси, нужно ли обновить существующий issue или создать новый.

### 2. Найти запись в vault

1. Открой `vault/GDM/roadmap/известные баги и технический долг.md`
2. Найди секцию с указанным ID (`$ARGUMENTS`)
3. Если запись не найдена — сообщи пользователю и выведи все доступные ID (grep по `### BUG-` и `### DEBT-`)

### 3. Собрать контекст из vault

1. Из найденной записи извлеки поле **Подробности** — это wiki-ссылка `[[...]]` на заметку в vault
2. Прочитай эту заметку (обычно в `vault/GDM/knowledge/debugging/` или `vault/GDM/knowledge/decisions/`)
3. Из заметки извлеки: симптомы, причину, воспроизведение, связанные файлы
4. Если заметки нет — работай только по записи в файле техдолга
5. Найди связанные BUG/DEBT: если в заметке или записи техдолга есть wiki-ссылки `[[...]]` на другие заметки из debugging/decisions, проверь — есть ли для них записи BUG-NNN/DEBT-NNN в техдолге. Если есть и для них создан GitHub issue (поле `**GitHub:**`) — запомни номера для раздела «Связанные issues»

### 4. Валидация упомянутых файлов

Для каждого файла, упомянутого в vault-заметке:

1. Проверь, что файл существует (Glob/Read). Если файл переименован или удалён — отметь в issue: `⚠️ файл X не найден, возможно переименован`
2. Если указаны конкретные строки — проверь, что на этих строках находится ожидаемый код (grep по ключевым символам). Если строки сдвинулись — укажи актуальные номера строк в issue

### 5. Проанализировать код

Для каждого **валидного** файла из шага 4:

1. Grep по ключевым символам (имена функций, переменных) — найди точные строки
2. Read фрагменты кода (offset + limit), чтобы понять контекст
3. Проследи цепочку вызовов: кто вызывает проблемную функцию, что происходит при ошибке
4. Найди связанные тесты: grep по тегам Catch2 (`[.tag]`) или именам тестов

### 6. Проработать варианты решения

Для каждого варианта опиши:
- **Суть** — что именно менять
- **Изменения** — конкретные файлы и строки
- **Плюсы/минусы** — trade-offs
- Рекомендуй комбинированный вариант, если применимо

### 7. Составить план решения

Разбей на этапы:
1. **Минимальный фикс** — чтобы тест перестал падать / проблема перестала проявляться
2. **Архитектурное исправление** — правильное решение
3. **Верификация** — тесты, сценарии, сравнение с аналитикой

### 8. Определить labels

Автоматическое определение labels по содержимому записи:

| Условие | Label |
|---|---|
| ID начинается с `BUG-` | `bug` |
| ID начинается с `DEBT-` | `enhancement` |
| Статус содержит 🔴 | добавить `critical` |
| Статус содержит 🟡 (обход есть) | добавить `workaround` |
| Поле **Блокирует** непустое | добавить `blocking` |

### 9. Создать GitHub issue

**В dry-run режиме:** вывести preview (title, labels, имя ветки, первые 20 строк body) и остановиться. Не создавать issue, не менять vault.

Сформируй тело issue в формате markdown и сохрани во временный файл (scratchpad).

Структура issue:
```
## Описание
(что происходит, критичность)

## Симптомы
(наблюдаемое поведение)

## Корневая причина
(цепочка вызовов, что именно ломается)

## Воспроизведение
(код теста, команда запуска)

## Затронутые файлы
(таблица: файл | строки | роль)
(⚠️ пометки для файлов, которые не прошли валидацию на шаге 4)

## Анализ вариантов решения
(для каждого варианта: суть, изменения, плюсы/минусы)

## План решения
(этапы: минимальный фикс → архитектура → верификация)

## Связанные issues
(Related: #N — для каждого связанного BUG/DEBT, у которого есть GitHub issue)

## Связанные заметки в vault
(ссылки на заметки)
```

Создай issue через `gh`:
```
gh issue create --repo ArturSalamatin/GDM \
  --title "<ID>: <краткое описание>" \
  --body-file <path-to-temp-file> \
  --label "<labels>" \
  --assignee "@me"
```

### 10. Обратная связь в vault

После успешного создания issue:

1. В записи техдолга (`известные баги и технический долг.md`) добавь поле `- **GitHub:** [#<номер>](https://github.com/ArturSalamatin/GDM/issues/<номер>)` к соответствующей секции
2. Если есть подробная заметка в `knowledge/debugging/` или `knowledge/decisions/` — добавь в неё строку `**GitHub issue:** [#<номер>](https://github.com/ArturSalamatin/GDM/issues/<номер>)`

### 11. Предложить ветку

После создания issue предложи пользователю создать рабочую ветку:

```
Создать ветку fix/bug-001/well-state-rollback для работы над этим issue?
```

Формат имени ветки: `<prefix>/<id-lowercase>/<slug>`
- `BUG-*` → prefix `fix` (например `fix/bug-001/well-state-rollback`)
- `DEBT-*` → prefix `refactor` (например `refactor/debt-007/amgcl-fetchcontent`)

Правила для slug:
- 2–5 слов через дефис, латиница, lowercase
- Отражает суть проблемы, не ID
- Без артиклей и предлогов

Ветку создавать только после явного подтверждения пользователя.

### 12. Сообщить результат

Выведи:
- URL созданного issue
- Присвоенные labels
- Краткую сводку: корневая причина, рекомендуемый вариант решения, количество этапов

## Режим new (свободный текст)

Когда `$ARGUMENTS` — не ID, а описание проблемы (например: `/issue Newton не сходится при переключении режима скважины`).

### 1. Определить тип и ID

1. Спроси пользователя: это баг (`BUG`) или технический долг (`DEBT`)?
2. Grep по `### BUG-` и `### DEBT-` в файле техдолга — найди максимальный номер
3. Присвой следующий свободный ID (например `BUG-003` или `DEBT-010`)

### 2. Собрать информацию

Задай пользователю уточняющие вопросы (через AskUserQuestion, одним блоком):
- Симптомы: что наблюдается?
- Воспроизведение: как вызвать?
- Связанные файлы: какие модули затронуты?

Если пользователь уже дал достаточно информации в тексте — не спрашивай повторно.

### 3. Проанализировать код

Аналогично шагу 5 режима existing: grep по упомянутым функциям и файлам, прочитать контекст.

### 4. Создать запись в vault

1. Добавь секцию с новым ID в `vault/GDM/roadmap/известные баги и технический долг.md` по формату существующих записей
2. Если проблема сложная — создай подробную заметку в `vault/GDM/knowledge/debugging/` (для BUG) или `vault/GDM/knowledge/decisions/` (для DEBT) и добавь wiki-ссылку
3. Обнови `vault/GDM/00-home/index.md` если создана новая заметка

### 5. Создать GitHub issue

Аналогично шагам 6–12 режима existing.

---

## Примечания

- Если `gh` не авторизован — предложи `gh auth login --web`
- Не используй спецсимволы PowerShell в теле issue — пиши в файл, передавай через `--body-file`
- Язык issue и vault-записей: русский
- Не создавай коммитов — только issue и vault-записи. Пользователь коммитит сам
- Тело issue сохраняй в scratchpad-директорию, не в проект
- PATH для gh может потребовать обновления: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
