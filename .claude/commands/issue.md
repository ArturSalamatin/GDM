# /issue – создать GitHub issue из записи в vault

Аргумент: `$ARGUMENTS` – идентификатор записи (например `BUG-001`, `BUG-002`, `DEBT-007`) **или** свободный текст описания новой проблемы. Флаг `--dry` в начале аргументов включает dry-run режим.

## Определение режима

- Если `$ARGUMENTS` начинается с `--dry` – режим **dry-run**: выполнить все шаги анализа, показать что будет создано (title, labels, первые строки body, имя ветки), но НЕ создавать issue, НЕ менять vault. Оставшаяся часть аргументов – ID или свободный текст.
- Если аргумент (после `--dry`, если есть) соответствует паттерну `BUG-NNN`, `DEBT-NNN`, `FEAT-NNN`, `VAL-NNN` или `RES-NNN` – режим **existing**: найти запись в vault и создать issue по ней.
- Иначе – режим **new**: создать запись в vault с новым ID и одновременно создать issue.

---

## Режим existing

### 1. Проверка дубликатов на GitHub

Перед любой работой проверь, нет ли уже issue для этого ID:

```
gh issue list --repo ArturSalamatin/GDM --search "<ID>" --state all
```

Если issue уже существует – сообщи пользователю URL и спроси, нужно ли обновить существующий issue или создать новый.

### 2. Найти запись в vault

1. Открой реестр по префиксу ID:
   - `BUG-` или `DEBT-` → `vault/GDM/roadmap/известные баги и технический долг.md`
   - `FEAT-` → `vault/GDM/roadmap/планируемые фичи.md`
   - `VAL-` → `vault/GDM/roadmap/валидационные кейсы.md`
   - `RES-` → `vault/GDM/roadmap/исследования и эксперименты.md`
2. Найди секцию с указанным ID (`$ARGUMENTS`)
3. Если запись не найдена – сообщи пользователю и выведи все доступные ID (grep по `### BUG-`, `### DEBT-`, `### FEAT-`, `### VAL-`, `### RES-`)

### 3. Собрать контекст из vault

1. Из найденной записи извлеки поле **Подробности** – это wiki-ссылка `[[...]]` на заметку в vault
2. Прочитай эту заметку:
   - BUG → обычно `knowledge/debugging/`
   - DEBT → обычно `knowledge/decisions/`
   - FEAT → обычно `knowledge/physics/` или `knowledge/decisions/`
   - VAL → обычно `knowledge/validation/`
   - RES → обычно `knowledge/numerics/` или `knowledge/physics/`
3. Из заметки извлеки контекст по типу:
   - BUG: симптомы, причину, воспроизведение, связанные файлы
   - DEBT: текущее состояние, мотивация, затронутые модули
   - FEAT: физическое обоснование, уравнения, зависимости, фаза roadmap
   - VAL: эталонное решение, сценарий, метрики, tolerance
   - RES: гипотеза, дизайн эксперимента, метрики, ожидаемый результат
4. Если заметки нет – работай только по записи в реестре
5. Найди связанные BUG/DEBT/FEAT/VAL/RES: если есть wiki-ссылки `[[...]]` на другие заметки, проверь – есть ли для них записи в реестрах. Если есть и для них создан GitHub issue (поле `**GitHub:**`) – запомни номера для раздела «Связанные issues»

### 4. Валидация упомянутых файлов (BUG/DEBT/FEAT)

Для типов VAL и RES – пропустить шаги 4–6 (у них нет «проблемных файлов» и «вариантов решения»). Перейти к шагу 7.

Для каждого файла, упомянутого в vault-заметке:

1. Проверь, что файл существует (Glob/Read). Если файл переименован или удалён – отметь в issue: `⚠️ файл X не найден, возможно переименован`
2. Если указаны конкретные строки – проверь, что на этих строках находится ожидаемый код (grep по ключевым символам). Если строки сдвинулись – укажи актуальные номера строк в issue

### 5. Проанализировать код (BUG/DEBT/FEAT)

Для каждого **валидного** файла из шага 4:

1. Grep по ключевым символам (имена функций, переменных) – найди точные строки
2. Read фрагменты кода (offset + limit), чтобы понять контекст
3. Проследи цепочку вызовов: кто вызывает проблемную функцию, что происходит при ошибке
4. Найди связанные тесты: grep по тегам Catch2 (`[.tag]`) или именам тестов

### 6. Проработать варианты решения (BUG/DEBT/FEAT)

Для каждого варианта опиши:
- **Суть** – что именно менять / добавлять
- **Изменения** – конкретные файлы и строки
- **Плюсы/минусы** – trade-offs
- Рекомендуй комбинированный вариант, если применимо

### 7. Составить план решения

Этапы зависят от типа задачи:

**BUG:**
1. **Минимальный фикс** – чтобы тест перестал падать
2. **Архитектурное исправление** – правильное решение
3. **Верификация** – тесты, сценарии, сравнение с аналитикой

**DEBT:**
1. **Подготовка** – baseline (тесты, производительность, API)
2. **Реализация** – инкрементальные изменения
3. **Верификация** – все тесты зелёные, поведение не изменилось

**FEAT:**
1. **Проектирование** – API, структуры данных, backward compatibility
2. **Реализация** – ядро → тесты → интеграция
3. **Верификация** – backward compat + новый функционал + аналитика (если есть)

**VAL:**
1. **Эталон** – подготовить/импортировать эталонное решение
2. **Сценарий** – создать тест-кейс в GDM
3. **Сравнение** – прогнать, собрать метрики, визуализировать

**RES:**
1. **Baseline** – контрольный прогон текущей реализации
2. **Эксперимент** – реализовать альтернативу, серия прогонов
3. **Анализ** – сравнить, сформулировать вывод

### 8. Сгенерировать имя ветки

Формат: `<prefix>/<id-lowercase>/<slug>`
- `BUG-*` → prefix `fix` (например `fix/bug-001/well-state-rollback`)
- `DEBT-*` → prefix `refactor` (например `refactor/debt-007/amgcl-fetchcontent`)
- `FEAT-*` → prefix `feat` (например `feat/feat-001/bhp-well-mode`)
- `VAL-*` → prefix `val` (например `val/val-001/buckley-leverett-1d`)
- `RES-*` → prefix `research` (например `research/res-001/upstream-vs-tvd`)

Правила для slug:
- 2–5 слов через дефис, латиница, lowercase
- Отражает суть задачи, не ID
- Без артиклей и предлогов

Проверь, что ветка не существует: `git branch --list "<имя>"`.

**Не создавай ветку** – это делает `/implement` (вместе с worktree). Здесь только фиксируешь имя: оно записывается в body issue, комментарий (шаг 11) и реестр (шаг 12).

### 9. Определить labels

Автоматическое определение labels по содержимому записи:

| Условие | Label |
|---|---|
| ID начинается с `BUG-` | `bug` |
| ID начинается с `DEBT-` | `enhancement` |
| ID начинается с `FEAT-` | `feature` |
| ID начинается с `VAL-` | `validation` |
| ID начинается с `RES-` | `research` |
| Статус содержит 🔴 | добавить `critical` |
| Статус содержит 🟡 (обход есть) | добавить `workaround` |
| Поле **Блокирует** непустое | добавить `blocking` |

### 10. Создать GitHub issue

**В dry-run режиме:** вывести preview (title, абзац «О чём задача» по правилам шага 13, labels, имя ветки, первые 20 строк body) и остановиться. Не создавать issue, не менять vault.

Сформируй тело issue в формате markdown и сохрани в `vault/GDM/issues/<id-lowercase>/01-issue-body.md` (создай каталог, если его нет). Файл в проекте, не во временном каталоге – см. «Файлы для `gh --body-file`» в примечаниях.

### 12. Обратная связь в vault

После успешного создания issue:

1. Добавь поле `- **GitHub:** [#<номер>](https://github.com/ArturSalamatin/GDM/issues/<номер>)` к секции в реестре:
   - BUG/DEBT → `известные баги и технический долг.md`
   - FEAT → `планируемые фичи.md`
   - VAL → `валидационные кейсы.md`
   - RES → `исследования и эксперименты.md`
2. Добавь поле `- **Ветка:** <имя ветки из шага 8>` к той же секции в реестре (рядом с **GitHub:**). Это позволит `/plan-*` и `/implement` найти ветку без обращения к GitHub.
3. Если есть подробная заметка в `knowledge/` – добавь в неё строку `**GitHub issue:** [#<номер>](https://github.com/ArturSalamatin/GDM/issues/<номер>)`

### 13. Сообщить результат

Отчёт **начинается** с ответа на вопрос «о чём задача»: пользователь должен понять её суть, не открывая issue. URL, labels и ветка – после.

Выведи по порядку:
1. **Заголовок** – `<ID>: <краткое описание>` и URL созданного issue.
2. **О чём задача** – связный абзац из 2–4 предложений, без списков:
   - что не так сейчас или чего не хватает (BUG – наблюдаемый симптом; DEBT – что плохо в текущем состоянии; FEAT – какой возможности нет; VAL – что не проверено; RES – какой вопрос открыт);
   - почему это важно – к чему приводит для расчётов, примеров, разработки;
   - что изменится после решения.

   Пиши своими словами по записи реестра и заметке vault; не повторяй заголовок и не копируй раздел «Описание» из тела issue.
3. Присвоенные labels.
4. Имя ветки (из шага 8).
5. Краткую техническую сводку по типу:
   - BUG: корневая причина, рекомендуемый вариант решения, количество этапов
   - DEBT: текущее состояние, целевое, количество этапов
   - FEAT: суть фичи, фаза roadmap, количество этапов
   - VAL: эталон, метрики, tolerance
   - RES: гипотеза, метрики, количество прогонов

## Режим new (свободный текст)

Когда `$ARGUMENTS` – не ID, а описание проблемы (например: `/issue Newton не сходится при переключении режима скважины`).

### 1. Определить тип и ID

1. Спроси пользователя: это баг (`BUG`), технический долг (`DEBT`), новая фича (`FEAT`), валидация (`VAL`) или исследование (`RES`)?
2. Найди максимальный номер в соответствующем реестре:
   - BUG/DEBT → grep `### BUG-` и `### DEBT-` в `известные баги и технический долг.md`
   - FEAT → grep `### FEAT-` в `планируемые фичи.md`
   - VAL → grep `### VAL-` в `валидационные кейсы.md`
   - RES → grep `### RES-` в `исследования и эксперименты.md`
3. Присвой следующий свободный ID

### 2. Собрать информацию

Задай пользователю уточняющие вопросы (через AskUserQuestion, одним блоком). Вопросы зависят от типа:

**BUG:**
- Симптомы: что наблюдается?
- Воспроизведение: как вызвать?
- Связанные файлы: какие модули затронуты?

**DEBT:**
- Что именно плохо в текущем состоянии?
- Какие модули затронуты?
- Есть ли обходные пути или workaround-ы?

**FEAT:**
- Какую задачу решает?
- К какой фазе roadmap относится?
- Есть ли зависимости от других FEAT/BUG?
- Есть ли аналитическое решение для верификации?

**VAL:**
- С чем сравниваем (аналитика, MRST, ECLIPSE)?
- Какой сценарий (сетка, условия)?
- Какие метрики и допустимая ошибка?

**RES:**
- Какая гипотеза?
- Что варьируем, что фиксируем?
- Что делаем с результатом (FEAT, изменение default)?

Если пользователь уже дал достаточно информации в тексте – не спрашивай повторно.

### 3. Проанализировать код (BUG/DEBT/FEAT)

Для типов VAL и RES – пропустить (аналогично шагам 4–6 режима existing).

Для BUG/DEBT/FEAT: аналогично шагу 5 режима existing – grep по упомянутым функциям и файлам, прочитать контекст.

### 4. Создать запись в vault

1. Добавь секцию в соответствующий реестр (по формату существующих записей):
   - BUG/DEBT → `известные баги и технический долг.md`
   - FEAT → `планируемые фичи.md`
   - VAL → `валидационные кейсы.md`
   - RES → `исследования и эксперименты.md`
2. Если задача сложная – создай подробную заметку и добавь wiki-ссылку:
   - BUG → `knowledge/debugging/`
   - DEBT → `knowledge/decisions/`
   - FEAT → `knowledge/physics/` или `knowledge/decisions/`
   - VAL → `knowledge/validation/`
   - RES → `knowledge/numerics/` или `knowledge/physics/`
3. Обнови `vault/GDM/00-home/index.md` если создана новая заметка

### 5. Создать GitHub issue

Аналогично шагам 7–13 режима existing (включая шаг 8 – генерация ветки; для BUG/DEBT/FEAT дополнительно шаг 6).

---

## Примечания

- Если `gh` не авторизован – предложи `gh auth login --web`
- Не используй спецсимволы PowerShell в теле issue – пиши в файл, передавай через `--body-file`
- Язык issue и vault-записей: русский
- Не создавай коммитов – только issue, комментарий и vault-записи. Пользователь коммитит сам
- **Файлы для `gh --body-file`.** `gh` принимает многострочный markdown только файлом: в PowerShell спецсимволы и кириллица в аргументе ломаются. Эти файлы – в папке проекта, `vault/GDM/issues/<id-lowercase>/`, с нумерацией по порядку публикации:

  | Файл | Назначение | Команда |
  |---|---|---|
  | `01-issue-body.md` | тело issue | `/issue` |
  | `02-comment-open.md` | «Контекст при открытии» | `/issue` |
  | `03-comment-plan.md` | «План готов» | `/plan-*` |
  | `04-comment-audit.md` | «Аудит плана» | `/audit-plan` |
  | `05-comment-done.md` | результат реализации | `/implement` |

  ⚠️ **Не использовать scratchpad, `/tmp` и другие временные каталоги.** Побочная польза от хранения в репозитории: видно, что именно опубликовано в issue и когда, без обращения к GitHub. Там же – пробы аудита (`probes/`, см. `/audit-plan`)
- PATH для gh может потребовать обновления: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`

## Следующий шаг: план

После завершения всех шагов (включая сообщение результата) – предложи пользователю создать план.

Определи команду по типу ID:
- `BUG-*` → `/plan-fix`
- `DEBT-*` → `/plan-improve`
- `FEAT-*` → `/plan-feature`
- `VAL-*` → `/plan-validate`
- `RES-*` → `/plan-research`

Спроси пользователя:
> Запустить `<команда> <ID>`?

Если пользователь подтвердит – вызови Skill tool с соответствующим именем и передай ID как аргумент.
