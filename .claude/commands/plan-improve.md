# /plan-improve — план рефакторинга, миграции или улучшения

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `DEBT-003`, `DEBT-007`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/GDM/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

---

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/GDM/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/GDM` → из title извлеки ID (формат: `DEBT-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/GDM/roadmap/известные баги и технический долг.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/GDM`
3. Прочитай подробную заметку из `knowledge/decisions/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Определить подтип

| Подтип | Признак | Пример |
|---|---|---|
| **Рефакторинг** | «разбить», «выделить», «переименовать», «монолит» | DEBT-003: ReservoirSimulator монолит |
| **Миграция** | «FetchContent», «заменить библиотеку», «перейти на» | DEBT-007: AMGCL → FetchContent |
| **Удаление** | «удалить», «убрать», «мёртвый код» | DEBT-004: DB-фабрики заглушены |
| **Кодировка/совместимость** | «wstring», «UTF-8», «кроссплатформенность» | DEBT-002: wstring в ядре |
| **Инфраструктура** | «CMake», «CI», «отладочный вывод», «test*.txt» | DEBT-009: test*.txt в cwd |

Подтип определяет шаблон этапов на фазе 3.

### 1.4. Извлечь имя ветки

1. Из GitHub issue или vault-записи (если `/issue` уже генерировал)
2. Если нет — сгенерируй: `refactor/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.5. Загрузить связанные заметки

1. Wiki-ссылки из заметки — прочитать каждую
2. Связанные BUG/DEBT/FEAT/VAL/RES — может ли текущая задача сломать обход другого бага или конфликтовать с текущей работой?
3. `vault/GDM/roadmap/стратегия тестирования GDM.md` — паттерны тестов
4. `vault/GDM/roadmap/инвентаризация кодовой базы*.md` — какие модули затронуты

### 1.6. Исследовать код

1. **Scope:** определи все файлы, которые будут затронуты. Для рефакторинга — grep по имени класса/функции во всём проекте. Для миграции — все include-ы и CMakeLists.txt
2. **Зависимости:** кто использует затронутый модуль?
3. **Тесты:** какие тесты покрывают затронутый код?
4. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности»

## Фаза 2: Анализ и проработка

### 2.1. Текущее состояние (baseline)

Зафиксируй текущее поведение:
- Какие тесты зелёные (`ctest --test-dir build -C Release | tail -5`)
- Производительность (если релевантно): время сборки, время тестов
- API/интерфейсы, которые используются внешним кодом

### 2.2. Целевое состояние

Опиши, как должен выглядеть код после изменений:
- Какие файлы появятся / исчезнут / переименуются
- Как изменится структура зависимостей
- Какие интерфейсы сохранятся / изменятся
- Что станет проще (тестировать, расширять, понимать)

### 2.3. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** — стратегия преобразования
- **Конкретные изменения** — какие файлы, какие преобразования
- **Промежуточные состояния** — можно ли разбить на этапы, каждый из которых компилируется и тесты зелёные?
- **Плюсы/минусы**
- **Риски** — что может пойти не так
- **Трудоёмкость** — файлы, строки

### 2.4. Выбор варианта

Критерии для DEBT (отличаются от багов):
- **Минимальность diff** — меньше изменений = меньше риск
- **Инкрементальность** — каждый промежуточный коммит компилируется и тесты зелёные
- **Обратная совместимость** — внешний API не ломается
- **Тестируемость** — результат легче тестировать, чем исходник

### 2.5. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Все call sites найдены:** grep по имени класса/функции, include-ы
- [ ] **Потокобезопасность:** OpenMP, shared state
- [ ] **Зависимости сборки:** CMakeLists.txt, include paths, порядок линковки
- [ ] **Обратная совместимость API:** вызывающий код не ломается
- [ ] **Тесты:** все существующие тесты продолжают компилироваться и проходить
- [ ] **Кодировки:** wstring ↔ string, UTF-8 vs cp1251
- [ ] **Платформозависимость:** Windows-only API, пути с `\`, `__declspec`
- [ ] **Мёртвый код:** убедиться что удаляемый код действительно не используется (не только в main, но и в тестах)
- [ ] **Связь с другими задачами:** не конфликтует ли с обходами других BUG/DEBT/FEAT/VAL/RES?
- [ ] **Производительность:** не деградирует ли (для миграций: новая версия библиотеки не медленнее)

### 2.6. Обнаружение новых проблем

В ходе анализа могут обнаружиться новые проблемы. Для каждой:
1. Зафиксируй в плане (раздел «Обнаруженные проблемы»)
2. Блокирует ли текущую задачу? Если да — включи в план как предварительный шаг
3. Если нет — после завершения плана добавь в соответствующий реестр

## Фаза 3: Детализация плана

### 3.1. Шаблон этапов по подтипу

#### Рефакторинг (выделение модуля):

1. **Подготовка** — ветка, зелёные тесты, baseline
2. **Создание нового модуля** — заголовок + пустая реализация, подключение в CMake
3. **Перенос кода** — по одному методу/блоку: вырезать из старого → вставить в новый → адаптировать
4. **Адаптация вызовов** — обновить все call sites, include-ы
5. **Тесты** — новые unit-тесты для выделенного модуля
6. **Очистка** — удалить дублирующийся код, обновить vault

Ключевое правило: **после каждого шага проект компилируется и все тесты зелёные.**

#### Миграция зависимости:

1. **Подготовка** — ветка, snapshot тестов и производительности
2. **Подключение upstream** — FetchContent/find_package в CMakeLists.txt, сборка с обеими версиями
3. **Локализация патчей** — если есть локальные изменения, оформить как `.patch` файл
4. **Переключение** — изменить include paths, убедиться что собирается с upstream
5. **Применение патчей** — PATCH_COMMAND или wrapper-header
6. **Тесты** — все тесты зелёные, производительность не хуже baseline
7. **Удаление локальной копии** — удалить старую папку, обновить .gitignore

#### Удаление мёртвого кода:

1. **Подготовка** — ветка, доказать что код мёртвый (grep, call graph)
2. **Удаление** — по одному файлу/классу, с проверкой сборки после каждого
3. **Очистка CMake** — удалить из target_sources, target_include_directories
4. **Тесты** — все зелёные
5. **Обновление vault**

#### Кодировка/совместимость:

1. **Подготовка** — ветка, инвентаризация: grep по `wstring`, `L"`, cp1251
2. **Конвертация** — по одному файлу: wstring → string, проверка сборки
3. **Адаптация интерфейсов** — изменить сигнатуры, вызовы
4. **Тесты**
5. **Очистка**

#### Инфраструктура:

1. **Подготовка** — ветка, понять текущее поведение
2. **Изменение** — CMake, пути, флаги, #ifdef
3. **Тесты**
4. **Очистка**

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение

**Файлы:** <полные пути>

**Контекст:**
Для читателя без контекста: что есть сейчас, что хотим,
почему именно так. Ссылки на vault-заметки.

**Что сделать:**
1. Конкретное действие с файлом, функцией, строкой
2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Сборка: `cmake --build build --config Release`
- Тесты: `ctest --test-dir build -C Release`
- Все тесты должны остаться зелёными (поведение не изменилось)

**Подводные камни:**
- <ссылки на чеклист 2.5>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Тестовая стратегия

Для DEBT ключевое — **тесты неизменности поведения:**

1. **Regression:** все существующие тесты зелёные после каждого шага (перечислить конкретно, какие тесты покрывают затронутый код)
2. **Unit-тесты нового модуля:** если выделяется новый класс/модуль — написать unit-тесты
3. **Smoke-тест миграции:** если меняется зависимость — тест что новая версия даёт те же результаты
4. **Инвариантные тесты:** если задача затрагивает вычисления — проверить что результаты идентичны baseline

Формат:
```
**Тест:** <название Catch2>
**Тег:** [<тег>]
**Файл:** tests/<файл>.cpp (существующий / новый)
**Сценарий:** <что проверяем — на уровне задачи>
**Setup:** <конфигурация — если применимо>
**Ожидание:** <конкретные числа, неравенства, или качественные свойства>
**Baseline:** <с чем сравниваем — существующие тесты, производительность>
**Backward compat:** <при каком параметре=0 проверяется — если применимо>
**Предотвращает:** <какую регрессию ловит>
```

### 3.4. Критерии завершения

- [ ] Все шаги выполнены
- [ ] Все существующие тесты зелёные
- [ ] Новые тесты зелёные (если есть)
- [ ] Старый код / зависимость удалены (если это было целью)
- [ ] CMakeLists.txt чистый (нет ссылок на удалённое)
- [ ] Визуальная верификация пройдена (если задача затрагивает вычисления)
- [ ] Vault обновлён: статус задачи, заметки
- [ ] GitHub issue закрыт (если создан)
- [ ] Производительность не деградировала (если применимо)
- [ ] Roadmap фаза обновлена (если задача входит в фазу)

### 3.5. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Создай ветку: `git checkout -b <branch>`
4. Собери: `cmake -B build -S . -G "Visual Studio 17 2022"; if ($?) { cmake --build build --config Release }`
5. Прогони тесты (baseline): `ctest --test-dir build -C Release`
6. Запомни количество тестов и время — это baseline
7. Начни с шага 1. После каждого шага: сборка + тесты
```

## Фаза 4: Верификация плана (3 раунда)

### Раунд 1: Полнота

- [ ] Каждый затронутый файл упомянут хотя бы в одном шаге
- [ ] Для каждого шага есть проверка
- [ ] Зависимости шагов — без циклов
- [ ] Все подводные камни (2.5) адресованы
- [ ] Критерии завершения проверяемы
- [ ] После каждого шага проект компилируется и тесты зелёные

### Раунд 2: Корректность

Общее (для каждого шага):
- [ ] Упомянутые методы/поля/типы существуют (grep)
- [ ] Типы совместимы
- [ ] Номера строк актуальны

Специфичное для рефакторинга/миграции:
- [ ] CMake-изменения корректны (target_sources, include_directories)
- [ ] Все call sites обновлены (не осталось ссылок на старые имена)
- [ ] Не нарушены инварианты вычислений (если задача затрагивает числа)

### Раунд 3: Автономность

Представь: Claude в новой сессии с compact-контекстом.

- [ ] Каждый шаг самодостаточен
- [ ] Полные пути к файлам
- [ ] Объяснено ПОЧЕМУ, а не только ЧТО
- [ ] Термины расшифрованы
- [ ] «Как начать работу» — конкретные команды
- [ ] Baseline зафиксирован (количество тестов, время)

Проблемы → исправить → повторить раунд.

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план
- Язык: русский
- Избыточность лучше недосказанности
- Инкрементальность: после каждого шага проект компилируется и тесты зелёные
- Если >15 шагов — разбить на под-задачи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
